# Explain the Number

- **开跑前先写下决策线。** 写明跑到什么结果会改变决策，以及噪声底线在哪里。只要多次运行间的波动区间大于效应本身，立刻停手。
- **追问一句「为什么不能再快一倍？」。** 点出卡住当前数字上限的具体资源或代码路径，比如单核 CPU、某把锁、磁盘、网络，甚至压测发压端自己。这个结论必须从运行期间抓到的 profile 或系统计数器里来，再对应回源码。光看代码猜出来的不算瓶颈限制因素。如果你答不出为什么这个数字没法好上一倍，那你根本没搞懂自己测出了什么。
- **列出这个数字还可能测成了别的东西，并逐条拿证据排除。** 常见嫌疑犯包括静默报错、被跳过或命中的缓存、压根没跑到的代码、没调优的一端（停在默认配置上）、环境噪声，以及端到端占比小到无关痛痒的局部环节。
- **数字和证据必须绑在一起。** 把运行次数、波动区间和瓶颈限制因素直接写进说明里，或挂上可查的产物链接。

只要涉及性能数字，就按 [benchmark-checklist](../benchmark-checklist/SKILL.md) `skill` 走完整流程。只要涉及 `eval` 结果，对各轮试验同样要追问，每一轮是否都真完成了任务，这个差距跨轮次、跨模型是否站得住脚，以及这个场景本身是否有代表性。

只要出现以下任一情况，就说明你跳过了这条原则。没定下能改变决策的目标线就开跑；拿出来撑腰的数字没写运行次数、波动区间或瓶颈限制因素；或者算出来省掉的时间，比被改动的那个环节原本耗时还大。

这条原则区别于 [Prove It Works](../principle-prove-it-works/SKILL.md)，后者验证的是产出本身真实有效。
