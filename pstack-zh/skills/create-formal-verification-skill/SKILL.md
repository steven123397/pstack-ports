# Create a formal verification skill

普通测试只检查有人恰好想到要写的那几个用例。形式化验证则检查划定范围里的**所有**情况：模型里每一种步骤交错顺序、上限内的每一个输入，或者全空间输入。本 `skill` 帮你从仓库里挑出最值得上形式化验证的那一块代码，验证它的核心性质，并留下一个项目级本地 `skill`，让下一个代理每次改这块代码时都能直接跑验证。写这份 `skill` 时，假定读者是一个在改代码半路上冷启动读它、从未见过你先前工作的代理；同时让用户无需学习形式化验证语言，就能看懂结果、信任结果并据此行动。

## 从代码里选定目标

能从代码库里看出来的自己查，只把你观察不到的地方拿来问用户。如果用户已经点名了某块区域或某个 bug，就从那里起步。

好目标是一条代码对外做出的关键承诺：一旦违背会严重伤害用户，且普通测试几乎碰不到把它跑崩的那条路径。挑仓库里含金量最高的那个目标，别挑最好验证的软柿子。

## 让问题本身决定用什么工具

挑能以最低成本回答这个问题的工具：模型检测器、定理证明助手、基于 SMT 的验证器或其他工具。要查事件会不会按糟糕的顺序交错发生，通常适合对着设计的精简模型跑模型检测器，无论项目用什么语言，TLA+ 都是这类问题的默认选择。要查代码本身在所有输入下的行为（如内存安全、溢出或数据结构不变量），通常适合直接跑在源码上的验证器。如果当前语言没有可用的源码级验证器，如实说明，并改用自动生成输入去测真实代码，别手写一个函数纸面模型充数。必须在任意规模下都成立、靠定界远远不够的性质，可能需要定理证明。优先选仓库开发者自己装得上、跑得动的工具，并向用户解释为什么选它。

## 一份过关的形式化验证要做到什么

- **忠于真实代码。** 模型或证明里的每一部分都要能对应到评审人打得开的真实源码行。验证里当成一个不可分割步骤的动作，在代码里也必须是一个不可分割步骤。命名直接沿用本仓库的词。
- **确实能跑挂。** 一道从未亲眼见过它失败的检查什么也证明不了。拿它守护的代码构造一个被故意改坏的变体（比如删掉一道检查或调换两步顺序），演示每条性质都能确实跑挂。
- **查出的问题就是问题。** 如果当前代码本身就违反了性质，直接用代码自己的语言带着反例路径报出来。绝不要为了凑通过去削弱性质或改模型，也不要在用户没要求时擅自改业务代码。
- **对验证范围说实话。** 明明白白写清验证了什么、在什么边界和假设条件下成立，以及没覆盖什么。通过只代表在模型或边界内成立，不代表整个系统永不出错。
- **不学验证语言也能读懂。** 用一句大白话讲清这条性质是什么，再用一句大白话讲清违背它会带来什么危害。反例路径用代码里的业务词写成一串简短步骤。
- **重跑成本低。** 一条命令即可执行、工具版本可复现，而且耗时足够短，确保下一个代理每次动相关代码都愿意跑它。
- **与代码保持同步。** 记清每道检查覆盖哪些文件和函数，以及你最后一次确认验证与代码一致的 commit。只要被覆盖的代码在那条 commit 之后又变了，下一个代理一眼就能看出需要重新校准验证。

## 生成项目本地验证 `skill`

写一份带 YAML frontmatter 的项目级本地 `skill`，在 frontmatter 里写清覆盖领域和触发时机（没有 frontmatter 就根本不会注册生效）。单靠这份 `skill` 本身，下一个代理必须能完成四件事：判断自己的改动有没有碰到已验证代码、跑起来验证、分清报错是真实 bug 还是建模误差，以及在有意改变业务行为时同步更新验证。把覆盖文件清单和同步基准 commit 直接写进 `skill`，并明确要求下一个代理只有在确认验证与新 commit 代码完全一致后，才允许把同步 commit 往前推。全篇使用本仓库真实的命令、路径和专名，不留任何占位符。

如果这道检查用的是 TLA+ 模型，要求下一个代理用 pstack 的 [`/statechart`](../statechart/SKILL.md) `skill` 来解读每一次运行结果。它能把模型检测器抓出来的每一条不变量违背，变成用大白话写的最短反例路径；检查通过时，`/statechart` 会画出系统在各状态之间流转的状态图。只按名字引用 `/statechart` 即可，它的命令、参数和文件路径会随版本和机器变化，绝不要把那些细节抄进生成的 `skill` 或脚本里。

## 交接前先拿真实破坏演练一遍

像下一个代理一样，照着刚生成的 `skill` 从头走一遍，在真实代码上做一处临时破坏（打破该性质），确认它能稳稳抓出这个破坏。随后撤销临时破坏，确认检查回到初始状态：要么通过，要么只报出你即将上报的既有发现。从未实际跑过的验证 `skill` 只算草稿。如果它没拦住临时破坏，或者某个步骤跑不通，修 `skill` 或修验证本身，别去迁就临时破坏。

## 交接汇报

向用户交代清楚：验证了什么、选了哪个工具及理由、验证边界、用大白话写出的检查结果、重跑命令，以及没覆盖哪些东西。只有在顺手发现了价值接近的第二个候选目标时才提议。最后向用户介绍 `/maintain-formal-verification-skill`，用于在后续绕过检查改了代码后重新把验证拉回同步。
