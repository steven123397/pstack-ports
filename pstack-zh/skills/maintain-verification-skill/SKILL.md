# Maintain a verification skill

只要应用一改，Feature Map 立马就会开始过时。本 `skill` 就是给 `/create-verification-skill` 生成的 `skill`（或任何带 Feature Map 的项目级本地验证 `skill`）准备的定期保鲜循环。严谨度的最小单位是「功能」，不是逐字抠句子：每个功能文件都要对着源码过一遍，再全部实操跑一遍，不要把每条要点死板机械化。

## 巡检结果枚举

三选一，并明确报出选了哪一个：

- **clean。** 每个功能都完成了源码核对和实跑覆盖，没有任何值得提交的偏移。不建分支，不开 PR。
- **changed。** 提且仅提一个 PR，合入全部经过实证的文档、`harness` 或 Feature Map 修正。
- **blocked。** 覆盖检查没能跑完，或某项已证实的修正无法安全交付。准确说明卡在什么地方。

## 允许编辑的范围

只允许编辑该验证 `skill` 自己的目录（它的 `SKILL.md`、`features/` 以及它自带的 `harness` 脚本）。巡检期间绝不要修改产品业务代码：如果 Feature Map 写的行为应用已经不再具备，要么是文档漂移（修正地图），要么是产品功能回归（如实上报，绝不在文档里替它遮掩）。

## 巡检流程

0. **定位目标。** 找到要维护的验证 `skill`，即正文带 Launch / Drive 章节和 Feature Map 的项目级本地 `skill`（通常位于 `.cursor/skills/verify-*/`）。命中多个候选时询问要维护哪一个；一个都没有时直接停下，指引去跑 `/create-verification-skill`，绝不凭空编一个目标。

1. **索引整洁度检查。** 通读 Feature Map 的 README 并列出同级目录的所有文件，修掉漏登记、多余、重复或失效的条目。轻量处理，不要自动生成清单脚本。

2. **源码巡检波次。** 每个功能文件派一个只读子代理，全部并发启动。每个子代理只看源码回答「这个面向用户的功能现在到底怎么工作？」，带出处标出疑似文档漂移，并交回一份精炼的实跑验证步骤。子代理绝不直接驱动应用，也绝不编辑任何文件。固定返回四段：功能摘要 / 源码入口 / 疑似漂移（或无）/ 一份实跑步骤。

3. **汇总对账。** 确认每个功能文件都收回了摘要。把重叠的实跑步骤尽量合并到最少的应用状态切换里。抽检标出来的疑似漂移；源码和文档本就一致的项不用反复重证。顺手扫一遍近期的频繁改动，排查有没有新冒出来的面向用户界面漏进 Feature Map；必须给出具体源码路径才能报「缺失」。

4. **实跑通测。** 哪怕源码看着全对，这一步也必跑。总控会话统一掌控全部实操驱动，严格遵守目标验证 `skill` 自己的 Launch 模型，服务与 UI 串行驱动单个常驻实例，短生命周期 CLI 则每次驱动起独立隔离会话（以目标 `skill` 的 Launch 章节为准，不以本节为准）。每个功能至少实跑一次，无论碰到什么故障，全程死守三条不变量：(1) 绝不驱动一个自从上次出现异常后就没跑过健康检查的实例，首次驱动前跑 `doctor`，按会话隔离时每个新会话都跑 `doctor`，任何一次驱动失败后再跑 `doctor`，遇到 `doctor` 看不出来的故障（比如进程活着但 UI 卡死），直接重置回已知干净状态或重启，绝不靠祈祷硬撑；(2) 到目前为止抓到的证据必须在每次清理后完好留存，亲自去指定路径核对，别靠猜；(3) 单次驱动拉起的一切东西都不能活过它有用的生命周期，哪怕会话卡死、异常退出或处于共享实例，都要清干净失败迭代留下的残局（共享实例只清残局，不杀共享实例本身）。如果 `doctor` 失败是由验证 `skill` 自身漂移导致的，把它当漂移处理，在允许编辑范围内修好后重试一次（只重启被本次修复影响到的部分，不多动别的），再决定是否判 `blocked`。无法触达的功能只有在给出具体未满足前置条件（鉴权、权限、操作系统、外部状态）和实际尝试路径后，才能标为 `verified-unreachable`；如果地图里本来就没写这条前置条件，那本身就算文档漂移。分诊阶段修过的任何 `harness` 问题，交付前都必须重新实跑验真。全部驱动（含复验）结束后做最后一次彻底清理，确保不留任何孤儿残留（同时按 `skill` 约定保留证据）。

5. **逐项定性（Triage）。** 用户视角描述有误或缺失，定性为文档漂移，直接修掉。功能本身正常但 `harness` 驱动不了，定性为 `harness` 缺口，直接修掉（修复后的辅助脚本遵守生成时的同一套规矩：带可执行权限，且在 `skill` 正文写明调用方式）。应用实际行为确实坏了，定性为产品缺陷，记下来报给用户，不放进本次 PR。

6. **交付或收尾。** 结果为 `changed` 时，把每个改过的文件重读一遍，提一个包含全部经实证修正的 PR。结果为 `clean` 或 `blocked` 时，不开 PR，如实汇报结论和实际覆盖情况。

把精炼的巡检笔记（已覆盖功能、不可达前置条件、已确认漂移、最终结果）记在临时目录里，不要提交进仓库。
