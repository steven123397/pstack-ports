# Build the Lever

只要活不琐碎，就造一个工具去干，别靠手工硬改。

一个 codemod、生成器或脚本每次跑出来的结果完全一致，重跑几乎零成本。工具本身就是一份评审人可读、可复跑的凭证。手工改出来的东西，想复核只能人肉再做一遍；一个确定性脚本，能把「信我没错」变成「你跑一下看」。

默认先造工具杠杆。只有在任务极其琐碎、一眼就能看完的那几处显而易见的改动时，才跳过这步。

- 先手工做完第一个样本摸清套路，再照着写出工具。拿工具对着这第一个样本重跑一遍，和你的手改版做 diff 验真。保证这个工具可安全重复运行。
- 代码改动用 codemod 或脚本，重复文件用生成器，数据分析就导进 SQLite 写查询，验证就做成可复跑的检查脚本。
- 能用确定性工具一趟跑完的活，别靠扇出子代理硬干。工具一次扫完所有单元就自己直接跑，别派一堆子代理去手工干脚本本来能干的事。
- 需要扇出交给多个子代理干活时，把工具杠杆写成一个让它们共读的 `skill`，把操作步骤、验收契约和禁改红线收进同一份产物里。把它放在子代理的写入范围之外，防止它们悄悄篡改契约。
- 用了这条 `principle`，diff 里就必须落下一个文件。如果你嘴上引用了它，diff 里却既没有 codemod、脚本、生成器，也没有给子代理的 `skill`，那你其实根本没用上。
- 只要这项工作在当前会话结束后还有用，就把这个工具一并提交进仓库。

要不要造工具，门槛在于「是否琐碎」，而不在于「是否重复」。哪怕是一次性任务，只要靠工具才能让结果经得起复核，就值得造一个。按 [Laziness Protocol](../principle-laziness-protocol/SKILL.md)，只写能干完或证明这件事的最小脚本，绝不要顺手搭一个框架。

这条原则区别于 [Encode Lessons in Structure](../principle-encode-lessons-in-structure/SKILL.md)。后者是把反复提醒的规矩固化成长效护栏，而这里解决的是眼前这项工作的吞吐量和可评审性。关于如何把验证本身脚本化，看 [Prove It Works](../principle-prove-it-works/SKILL.md)。
