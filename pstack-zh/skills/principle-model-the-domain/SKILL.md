# Model the Domain

把真实的领域逻辑编码进数据结构，别让它散落在一堆条件判断里。贴合领域的数据结构能让非法状态在类型上无法构造，顺手删掉大批分支。写代码时就把结构选对成本很低；留到以后再收拾，就会变成一项一拖再拖的重构工程。

优先选用下面这些手段：

- 用状态机，别用四处散落的布尔标志、阶段字段或生命周期判断。
- 用强类型模型，别用松散参数或在各处重复假设数据形状。
- 用映射表、注册表、查表结构或可辨识联合（discriminated union），别让分支判断散落在多个文件里。
- 用 reducer 或命令/事件模型，别到处随手改状态。
- 围绕一整块领域知识来组织模块，别按「加载、校验、转换、保存」这种执行流程切模块。执行顺序不等于归属边界。
- 划出一个紧凑的模块边界，把重复行为、归属关系和不变量收拢到一处。
- 访问模式需要时，直接上队列、缓存、索引、图、树或规范化集合。
- 其他贴合场景的结构也可以。如果现成结构都不合适，就先理清代码绝不允许出现什么状态、数据会被怎么读取，再找出正好能把这两件事编码进去的结构。

不要硬凑抽象。如果现有形态已经清晰、局限在局部，而且大概率不会继续膨胀，老老实实写直白的代码就行。如果一个抽象只增加了间接跳转，却没有删掉任何分支、重复规则、非法状态或生命周期风险，就要对它保持警惕。

跳过了这条原则的典型信号，就是每加一个新功能都要往现有的 if/else 链里再塞一个分支，或者多出一个必须和第一个布尔值保持同步的第二个布尔值。按时间阶段拆模块（temporal decomposition）也是信号，按阶段命名的模块往往会把同一套领域规则在每个步骤里抄来抄去。
