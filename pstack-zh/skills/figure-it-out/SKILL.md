# Figure it out

当手头任务套不上任何现成 `playbook` 时，现设计一套。动手写第一行代码之前，你要先交出来的东西就是工作流本身，即一串按任务体量匹配严谨度、遵循科学实验方法、并留下决策轨迹的阶段清单，好让人离开一阵再回来时能从头审计。

## 开工起手式

先建一份待办清单，第一项固定是通读 **poteto-mode** `skill` 的 Principles 章节，然后把下面五个阶段加进待办。

## Phase A：定框与边界

先摸清底细再立项。在说清楚下面三件事之前，别开跑：

- 把完成判定写成可证伪的条件（参见 **prove-it-works** `principle` `skill`）。
- 量化范围，列出大致的工作单元数、工作量估算，以及摸底阶段发现的阻塞项。
- 定好严谨度档位，宁高勿低。不可逆决策和高影响面改动把严谨度拉高，可撤回的低风险步骤可以放轻。所谓严谨度，靠的是卡点和留痕产物，不是喊一句「再加把劲」。

准备开跑长周期任务前，先把边界定框和权衡亮出来。可撤回的工作直接推进（参见 **never-block-on-the-human** `principle` `skill`），但动辄几小时的大工程值得留一道人工确认卡点。

## Phase B：设计工作流

把任务拆成原子化、可独立合入的单元，按「风险最高、未知最多优先」的顺序排列。脚手架和验证基础设施排在业务功能前面（参见 **foundational-thinking** `principle` `skill`）。

- 开干之前先把验证 `harness` 搭起来，并从改动前的状态抓好基线，让后续每次检查都能直接呈现「旧值 vs 新值」。
- 碰到不可逆的架构决策，调用 **architect** `skill`（它内部会跑 **arena**）。对于形态已经很具体的机械活，跳过这步。对已经拍板的设计再跑第二轮 `arena` 属于过度设计（参见 **laziness-protocol** `principle` `skill`）。
- 决定哪些环节需要扇出。只在天然解耦的接缝处并行，给每个工人独立的 `worktree` 或分支（参见 **separate-before-serializing-shared-state** `principle` `skill`），别过度扇出。按 **poteto-mode** `skill` 的 Subagents 章节，为每个子代理选定匹配的推理档位。
- 把设计好的阶段清单明确写下来。这份清单就是给人审的。

接着按设计执行。把具体步骤作为待办项插在 Phase C 和 Phase D 之间。每一步都在 Phase C 的实验循环纪律下执行，同时把 Phase D 的日志记录织进每一步里，每落一步就记一行，绝不要攒到最后再补整份记录。

## Phase C：跑实验循环

每个单元都是一次独立实验。先写明假设，做最小改动，在真实产物上拿完成判定实测，往前推进了就保留，没推进就回退。贯彻 **sequence-verifiable-units** `principle` `skill`，每做完一个单元就立刻验证，再开下一个，绝不攒到最后一起验。

- 验证必须直接检查真实产物，绝不轻信口头自报。如果某件事通过得太轻松，先怀疑你的观测手段，再怀疑被测系统。
- 委派出去的活要配一位裁判。如果工人钻了卡点的空子，重置进度并加固契约；如果卡点本身写错了，单开一次改动修好卡点，别绕路躲过去。
- 判定结论只能是 `VERIFIED`、`NOT VERIFIED` 或 `INCONCLUSIVE`。`INCONCLUSIVE` 不算通过，别把负面结果藏起来。

## Phase D：维护审计轨迹

用 **show-me-your-work** `skill` 全程记录运行日志。走到 `figure-it-out` 这个量级的任务，通常都足够复杂，值得把决策日志一并提交进仓库，方便评审人在 PR 里直接查阅。决策轨迹加上 diff，才是人回来后敢放心信任你产出的底气。

## Phase E：整体验收与交接

拿整个结果在真实产品上（而不只是在测试 `harness` 里）对照 Phase A 的完成判定过一遍。把过程中反复出现的任何纠偏，都固化成门禁、lint 规则、校验项或脚本（参见 **encode-lessons-in-structure** `principle` `skill`）。

**回复要求：** 交出你设计好的 `playbook`、选定的严谨度档位及理由、决策日志路径、对照完成判定已验证通过的项，以及仍未解决的遗留项。
