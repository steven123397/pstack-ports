# 怎么把 `prompt` 写到位

一条 `prompt` 只需交代意图和完成判定。具体步骤由 `playbook` 兜底，几句大白话远胜长篇规格文档。

## 该写进去的五样

- **目标。** 直说哪里坏了，或者想要什么结果。
- **完成判定。** 必须能跑出通过或失败。「弄好一点」或给个时长都不算判定条件。
- **想看的证据。** 明确要真实命令输出、流程录屏、落库实值，或优化前后的实测对比数。
- **已知线索。** 症状、复现步骤、日志片段或相关链接，都能省掉代理一轮盲找。
- **真实约束。** 「先复现」「先别改代码」「零行为变化」「继续前先让我看一眼」，每一句都会实际改变代理的动作。

## 该省掉的三样

- **具体实现手段。** 说清要达成什么结果，给代理留空间去想比你更好的解法。
- **手列一串 `skill` 或步骤。** 自己排顺序很容易打乱或漏掉 `playbook` 本来会守住的关键步骤。只有想刻意覆盖某一项默认选择时才点名 `skill`。
- **你猜的根因（至少一开始别说）。** 先抛出猜测会把代理的搜索视野框死，等它自己复述完问题再聊你的直觉。

## 先把上下文喂足

- 面对杂乱的问题反馈，先让代理用大白话复述底层到底出了什么问题，再动代码。理解错了当场就能抓出来，零代码返工成本。
- 新开对话接旧活时，先 `/recall` 拼回这个话题的历史进度。旧对话里有很多新代理不知道的背景。
- 改陌生代码前，先用 `/how` 摸清运行机制，用 `/why` 查明历史缘由。脑子里没有模型就改代码的代理，多半只会对着表面症状打补丁。
- 用 `/teach` 让代理做论证，比如「说服我这修的是根因而不是症状」。一份可拷问的论证比平铺直叙的摘要更好核查。

## 先敲定设计，再出计划

- 永远别直接接受第一个设计。多要几个原型方案（UI 改动附截图或录屏），看着跑出来的实证挑。
- 开放问题拿原型跑明白，别对一份没写过代码的纸面计划做对抗评审，那只会凭空编出一堆永远不会发生的风险。
- 做共享包或 API 时，先让代理写出 README 或上手教程，再倒推内部实现。文档本身就是事后验收的具象靶子。
- 等设计真正稳下来再要实施计划，且计划里的每一步都必须以可检验的检查项收尾。

## 上下文齐了就短说

- 对话里已经明确任务时，「就这么办」「继续」「一直跑到完成」本身就是完整 `prompt`。
- 切换话题时开头带一句「新任务（new task）」，否则模式会把你的新消息当成上个任务的下一步。

## 离开前交代清楚

- 开头说「我要睡了（im going to bed）」或「我先走开一下（im stepping away）」，让代理别卡着等人请示。
- 把完成标准写成每轮循环都能跑的检查项，并把它作为 `/loop` 的判定条件。
- 让它基于指定 base 分支拉一个全新的 `worktree`。
- 把它本来会停下来请示的权限提前批掉，比如「提交 commit 前不用问我」。
- 要求记一份决策日志方便回来审计。
- 留好止损退出条件：「如果跑了几个小时确实卡死了，停下来把原因写清楚」。

## 一句话中途纠偏

- 重申目标：「我说的是先复现，还没让你直接改代码。」
- 点名 `principle`：「按 Prove It Works 来，给我看真实输出，别拿编译日志糊弄。」
- 点名管用是因为代理开工前已经读过细则，回复里也必须写明这条原则到底改变了哪个决定。
