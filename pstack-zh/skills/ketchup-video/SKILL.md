# Ketchup video

遵循 [`/ketchup`](../ketchup/SKILL.md) 的全部原则，但把其中的文字摘要和静态配图换成一段带字幕的短幻灯片视频。回溯时间窗口从用户在 `/ketchup-video` 之前发的最后一条消息算起，不是从更早的 `/ketchup` 算起。在仓库目录之外编写和渲染视频，是唯一允许打破只读规则的例外。最终回复由四部分组成：`ketchup` 的开篇一句话、内嵌视频、一行写明你自己还能接着干的剩余工作，以及待拍板事项清单。如果视频里展示了决策的各个选项，正文里直接沿用视频给每个选项起的名字。如果视频渲染失败，用一行话如实说明失败，然后只交出待拍板事项。

## 幻灯片设计

直接拿本次工作产出的真实截图、录屏、diff 和数据当素材，别照着聊天记录里的文字现编。动手画图前，先在草稿里写下「用户看完唯一要带走的那一句话」以及每张幻灯片的一句话大纲，凡是不改变用户认知的页面直接砍掉。总页数不超过 10 页，越精炼越好。这两份草稿笔记不要放进回复里。

每张幻灯片只讲一个点。尽量围绕同一张主画面逐页演进变化，别一页切一个互不相关的画面。同一种颜色或形状在整套幻灯片里必须始终代表同一个含义。用画面把工作讲出来，比如系统运转流程、带各 PR 状态的 PR 栈、修复前后对比，或者方案并排对比。用箭头、高亮和过渡动效指明哪里变了。幻灯片绝不能做成项目符号列表、状态清单、表格，或者一堆没有连线的孤立方块。

把画面文字压到最少。每个标签直接贴在它指代的物体上，用大白话写，别写「Tests: pass」这种生硬标签。别给图片本身已经画出来的东西再配说明词，也绝不要在多页幻灯片之间或下方正文里重复同一条事实。

逐一展示用户交代的每件事落成了什么结果，以及当前处于已完成、仍在运行、已失败还是尚未验证状态。还在等用户拍板的事绝不能标成已完成。顺手揪出并修掉的 bug 也要展示出来。如果某处可见改动没有截图，直接在对应页面标明，并写清屏幕上具体变了什么。全部内容只基于手里真实事实绘制，绝不编造数字，绝不伪造你没实际截过图的界面。

## 字幕规范

每张幻灯片配一行简短字幕，长度控制在十个词左右（一句简短大白话），只依据当前页面画出来的内容，用跟用户当面说话的口吻点出这页的重点。说清楚画面意味着什么，别把图上的标签照念一遍。把字幕放在画面正下方的独立字幕条里，每一页的字幕条高度保持完全一致，里面除字幕外留空，确保字幕绝不遮挡画面主体。字号放小但清晰，保证在聊天窗口尺寸下直接播放也能一眼看清。

## 渲染与自检

渲染成单个无声横屏视频（如 mp4），页与页之间带过渡动效。每一帧都是顶格铺满画面的幻灯片，正下方紧接字幕条。直接从幻灯片素材生成视频帧，绝不要靠录屏凑合，并把每页字幕硬烧录进对应帧里，保证字幕在整页停留期间全程可见。所谓停留时间（hold），是指一页完整呈现在画面上的时长，不算切入和切出动画。每页停留时长必须足够读完它新增的全部文字，至少每三个词给一秒（中文按自然阅读语速留足同等余量）。一页「新增的文字」包含本页字幕以及上一页还没出现过的所有文字（含内容发生变化的标签）；第一页所有文字都算新增；嵌入截图内部的文字不计入。

把视频内嵌发出去之前，必须亲自核查渲染好的成品文件。在聊天窗口实际展示尺寸下逐页抽看一帧，确认字幕清晰可读且没有遮挡任何内容。通过把视频帧与原始幻灯片比对来精确测量每页真实停留时长，别依赖静止帧检测器（它会把淡入淡出末尾极淡的过渡帧误算成静止）。把每页新增词数对照实测停留时长逐一过账。凡是规定时间里读不完的页面，改完重新渲染、重新核查，直到全部达标。
