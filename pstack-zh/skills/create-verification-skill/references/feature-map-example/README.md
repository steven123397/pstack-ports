# Notes 验证地图（Feature Map 示例）

本目录是验证 Notes 面向用户行为的长期维护权威源。驱动应用前先通读索引，再按对应功能文件里的步骤执行。

## 基线前置条件

- 在 `http://127.0.0.1:4173` 启动 Notes，并使用一次性临时数据目录。
- 设置 `NOTES_DATA_DIR=/tmp/notes-verify-$RUN_ID`，防止并发运行共享状态。
- 预置两条种子笔记，标题分别为 `Quarterly plan` 和 `Grocery list`。
- 确保 `control-notes` 和 `notes` CLI 已加入 `PATH`。
- 运行 `control-notes doctor`，确认返回预期的 URL、数据目录和构建版本。
- 绝不驱动并非由本次验证运行启动的应用实例。

## 驱动约定

- 除非某个功能的 `Preconditions:` 另有说明，每个验证步骤都从基线状态起步。
- 优先使用 ARIA role 和无障碍名称，避免 CSS 选择器或 DOM 位置索引。
- 所有命令按字面原样执行，不要改动引号里的名称和参数标志。
- 浏览器操作统一通过 `control-notes browser` 执行。
- 终端操作统一通过 `control-notes cli -- <command>` 执行。
- 涉及数据写操作后恢复种子数据；清理阶段绝不删除实证产物。

## 实证与跳过上报规范

- 同时记录用户动作和动作后的结果状态，别只截最后一张屏幕。
- UI 实证必须包含 ARIA 快照，以及能看出应用身份标识的截图。
- CLI 实证必须包含完整命令、stdout、stderr 和退出码。
- 写操作实证必须包含从第二个只读视图回读落盘结果的证据。
- 每份产物都要标明对应的功能 ID 和所用入口。
- 遇到无法触达的路径，上报尝试过的命令和未满足的前置条件。
- 绝不要把跳过未测的入口靠另一个入口的结果报成「已验证」。

## 功能条目契约

每个功能文件以一个 H1 标题和一段描述用户可见行为的导语开头，接着严格按顺序包含四个 H2 章节：

1. `Sub-features` 用简短 ID 逐行列出每项子行为。
2. `How to get to it (user POV)` 列出用户能进入该功能的全部入口。
3. `Driving it with <harness>` 以 `Preconditions:` 开头，接着用带标签的要点把每个用户动作与确切命令、可观察结果一一配对。
4. `Gotchas` 列出可能白耗时间或让验证失效的暗坑。

地图里不写内部实现细节，只记录用户路径、稳定句柄、所需状态、确切命令和可观察实证。

## 功能列表

- [Create a note](./create-note.md) 覆盖浏览器与 CLI 创建、取消草稿、持久化校验与清理。
- [Search notes](./search.md) 覆盖工具栏、快捷键与 CLI 搜索，含命中、空结果与清空状态。
