# Create a verification skill

每一个严肃项目都需要一套脚本化手段去实操运行真实应用并证明行为正确：启动它、像用户一样走完核心功能，并留下实证。本 `skill` 会为当前仓库量身生成这样一个项目级 `skill`（`.cursor/skills/verify-<app>/`）。你写出来的东西是给下一个代理读的，不是给人读的：它会在任务中途被一个从未见过这个应用的冷启动代理直接拿起来用。

## 1. 盘问代码库，别先盘问用户

能从代码库里查出来的全部自己查，只把你观察不到的地方拿来问用户：

- **交互界面（Surface）：** 用户实际接触的是什么？Web UI、CLI/TUI、桌面应用、API、移动应用还是库？一个仓库可能有好几个，挑出主界面并注明其余的。
- **启动方式（Run）：** 应用怎么在本地起起来？优先采用仓库自己文档化的开发启动命令（package scripts、Makefile、README quickstart），记清端口、环境变量、种子数据和鉴权方式。
- **驱动手段（Drive）：** 代理怎么通过程序操作它？优先复用已有测试 `harness`（Playwright/Cypress 用例、expect 脚本、PTY 辅助工具、可直接 curl 的接口、调试端口）。实在没有再选通用方案：Web 和 Electron 用浏览器/CDP，CLI/TUI 用 tmux/PTY `harness`，后端服务用纯 HTTP。
- **观测证据（Observe）：** 能抓到哪些实证？截图、终端输出记录、响应体、日志、退出码、数据库状态。
- **实例隔离（Isolate）：** 两个实例能不能并排同时跑（端口、数据目录、用户配置）？如果不能，在生成的 `skill` 里明确写死：宁可拒绝并发驱动同一个共享实例，也绝不把用户正在用的会话搞坏。

如果当前检出的代码本来就编不过或起不来，先修好（或精确报错）再生成 `skill`；对着坏底座写出来的 `skill` 只会教出一套错步骤。如果仅仅是某个无关的缺失资源挡住了启动（比如 API 根本不对外提供的静态目录、一份示例配置），生成的 `skill` 可以自动创建它，明确标成验证脚手架，并在清理阶段删掉。

## 2. 生成验证 `skill`

写入 `.cursor/skills/verify-<app>/SKILL.md`，必须带 YAML frontmatter（包含 `name: verify-<app>`，以及写清应用名、交互界面和触发时机的 `description`，没有 frontmatter 就根本不会注册生效），并包含以下六个章节，每节全部落自第 1 步实测摸底（不留任何占位符）：

- **Launch：** 用于验证的确切启动命令，以及如何判定真正就绪（某条日志行或提示符）。启动流程必须能从空数据目录一路走到可用状态，涵盖所有数据库迁移和种子数据。所谓就绪是指真正可用，不只是进程端口能连上；数据库健康检查通过时，初始化脚本可能还在跑。同时写清停机步骤。对于短生命周期的 CLI 或 TUI，不存在常驻服务，Launch 指的是先编好二进制（或装好依赖），再为每次实操开启独立的 PTY 或 tmux 会话。
- **Doctor：** 一条只读健康检查，用来回答「眼前这个实例值不值得驱动？」包括进程存活、版本或构建正确、端口确实归本次启动所有、鉴权有效。只要代理觉得任何地方不对劲，第一步先跑它。
- **Drive：** 填入本仓库真实选择器与命令的驱动方案，绝不写泛泛示例。优先使用稳定句柄（ARIA 标签、data 属性、提示符字符串、路由路径），别依赖像素坐标或 Tab 键顺序。
- **Evidence：** 写清做实证需要抓哪些产物以及存到哪里。立死验证标准：必须走真实用户路径，别走内部 setter 或测试专用后门接口；同时记录触发动作和结果状态，别只截最后一张结果屏；除了肉眼可见的界面，一并核实副作用（写出的文件、插入的数据行、发出的消息）；只有在生产边界本身已经隔离了外部系统时才允许 mock。如果安全路径依赖 dry-run 或测试模式，别轻信名字，亲自观察（文件、网络、Git refs）确认它到底跳过了什么，不少 dry-run 照样会发网络请求或弹浏览器。
- **Cleanup：** 写清如何清理本次运行拉起的实例。绝不要按进程名乱杀，只杀你自己启动的实例。清理只删实例和临时状态，绝不删证据，实证产物必须在清理结束后依然完好保存在 `skill` 指定的目录里。
- **Helpers：** `skill` 附带的每一个脚本都必须带可执行权限，并在 `skill` 正文里给出确切调用方式。需要读者自己逆向研究才能用起来的脚本不算辅助脚本。

## 3. 初始化 Feature Map

创建 `.cursor/skills/verify-<app>/features/README.md`，再为你识别出的每个面向用户的功能建一个独立文件（先从路由、命令、菜单或文档里挑出前 3 到 5 个核心功能起步）。格式照 [`references/feature-map-example/`](references/feature-map-example/) 走，一份 README 索引加每个功能一份文件。每份文件从用户视角回答四件事：这个功能是什么、用户怎么走到它、如何用 `harness` 驱动它，以及什么可观察终态能证明它真的工作。固定使用四个 H2 标题：`Sub-features`、`How to get to it (user POV)`、`Driving it with <harness>` 和 `Gotchas`。如果种子数据缺了某条流程需要的前置条件，流程直接报失败，并把原因记进该功能的 `Gotchas`，绝不要削弱流程去硬凑通过。这份 Feature Map 是仓库长期维护的验证权威源；如果地图里列了好几个入口，只测了最省事的那一个就算验证不完整。

## 4. 交付前先亲自跑通一遍

照着刚刚生成的 `skill` 说明从头到尾真跑一遍：Launch、Doctor、驱动地图里的**一个**功能（跑通一个就够了，地图本身就是留给后续运行覆盖其余功能的）、抓证据、做 Cleanup。清理完成后，核实证据文件依然完好留在指定路径，把证据一起删掉的清理步骤直接算不通过。凡是跑挂的地方立刻修，而且每次失败迭代后也要跑生成的清理步骤，防止坏尝试遗留孤儿进程和死端口。从未执行过的验证 `skill` 只算草稿，不算交付物。如果你是在替身环境里跑通的（比如用容器代替全新虚拟机、用本地栈代替远端环境），把替身环境帮你做了、而真实目标环境不会做的每一项初始化步骤全部列出来，这些步骤在真实目标环境跑通前都算未验证。

## 5. 提示后续维护循环

向用户介绍 `/maintain-verification-skill`，用于在应用演进后持续让 Feature Map 保持真实有效。只在用户主动询问时才建议运行频率。
