# Blast radius

在代码合入上线前，查出它会在别处把什么搞坏。适用于「X 的影响面有多大」「这改动能把什么搞坏」，或者审查一个你心里没底的小 diff。

它是 `how` 和 `why` 的搭档。`how` 告诉你代码怎么跑，`why` 告诉你当初为什么长这样，`blast-radius` 告诉你它一动会震坏别处的什么东西。

把调用方列一张清单不算完成任务，代理一秒钟就能 grep 出来。真正的活，是找出 grep 根本扫不出来的隐患。

## 别轻信你自己写的分析

一篇写得头头是道的影响面分析毫无价值，因为不管真假，它读起来都很像那么回事。所以别光交一份文字分析。找出整件事赖以成立的那一两条核心事实，然后跑真实代码把它证出来。

### 你到底有多确定

对改动安全性所依赖的每一条事实，只要成本低，就尽量往下推到最深一级，并老实标明停在了哪一级。

1. 全凭嘴说。单靠这一级毫无价值。
2. 指出了具体代码行。给出真实的 `file:line`，或所调第三方库的源码位置。
3. 推演证明坏情况走不到。一步步走完故障路径，确认它到不了。
4. 实跑验证了。写脚本或测试调真实代码，一旦判断错了就会响亮报错。
5. 在真实运行的应用里复现了。

第 4 级通常只需要写一个很短的脚本，直接 import 应用实际打包的那个库，调你担心的那个具体函数。

## 执行步骤

1. 读透这次改动。看 diff，看它新增、修改、删掉了哪些符号，看它现在有哪些行为变了，尤其是 diff 字面上没直说的隐含变化。把整个 PR 和里面每一条 commit 都拉出来看。
2. 找出它之所以安全的那一条核心事实。大多数看着吓人的改动，其实都靠一条关键事实兜着，比如「这个调用只清理已经失效的缓存项，别的什么都不干」。把这条事实找出来。只要它成立，一大半看着危险的场景就同时解除了。把精力砸在这里，别列一长串「也许会坏」的清单。
3. 往 grep 扫不到的地方挖。去读你调用的库源码，核对它的锁定版本和本地 patch。理清执行时机，比如微任务、组件卸载与清理、Solid 和 React 的差异。顺着符号搜索抓不到的链路往下追，包括 API 返回的 JSON、数据库列、协议线格式、另一种语言在读的同一批字节、feature flag，以及往下跳了三层的下游代码。
4. 对每一项风险说真话。给出它真实的发生概率和出事后的真实代价。把你确认成立的风险留下来，把查过并排除掉的单独列开。每条都引真实的 `file:line`；搜完确认没有命中同样是有效结论，绝不要瞎编调用方或 API。
5. 证明那条核心事实。写个脚本或测试去跑真实代码，跑完把实际输出原样贴出来。
6. 如果改动体量大、波及面广，按 `arena` 模式来跑。拿同一个问题问不止一个模型，再把答案合并起来。不同模型能抓出不同的真 bug。

## 交付内容

- **它改了什么。** 改动内容，包括字面上不明显的那部分。
- **它之所以安全的那一条核心事实。** 把事实写出来，标明你推进到了第几级，附上实证。如果没证出来，直接写「未证实」。
- **确认的风险。** 每条写明会怎么坏、具体 `file:line`、概率和严重度，以及怎么检查。关键风险直接贴出验证证据。
- **已排除项。** 你查过哪些点、凭什么判断它们没问题。
- **合并前建议。** 能抓出真 bug 的最低成本测试或复现方式，连同你写的验证脚本一起附上。

全文过一遍 `unslop`，只引用真实代码；内容要发到公开场合前，先把所有内部敏感信息脱敏。

**回复要求：** 交出上面这套结构化分析，其中那条核心安全事实必须明确给出实证，或者老实标为「未证实」。
