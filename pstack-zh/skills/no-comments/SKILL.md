# No comments

派发 Comment Sicko，并根据审核采纳的发现动手整改。

充分尊重 Comment Sicko 的全新旁观视角。

## 范围

优先采用调用方指定的具体文件或 diff。否则默认取当前相对基线分支（默认 `main`）的完整 diff，包含未提交的工作区改动。

## 执行步骤

1. 派发 `Task`，指定 `subagent_type: "comment-sicko"` 并传入范围。按 **poteto-mode** `skill` 的 Subagents 章节，为每个子代理选定匹配的推理档位与 fast/standard 速度。不要重复复述它自己的规则。
2. 审核它的报告与 diff。凡是出现以下情况一律驳回：擅自修改业务代码、越出指定范围、误删受例外保护的注释、写错 `MUST KILL` 理由，以及把特意保留的合理代码当成问题来标。对「自家代码里出人意料的怪逻辑」打出的重塑标记依然算有效待办，别把那些废注释恢复回去。一条保留（keep）只有在拿得出证据证明它写的是「我们管不着、改不了的外部限制」时才能过关。顺带审计它有没有漏掉范围内的 lint 和 TypeScript 抑制注释；涉及正确性或安全性的抑制注释依然属于必须处理的 `MUST KILL`。只有在符合确切例外条款且有范围内实证时，才恢复被删的注释。在采纳依据单薄的 `IMPORTANT` 或 `do not remove` 类删除或保留判定前，先追踪对应符号或对它跑一遍 `/why`。如果一条删除判定存疑，不要恢复；如果一条保留判定被证伪或依然含糊不清，直接删掉。碰到被驳回的报告，回退它做的改动、指明具体失败点并重跑一次。如果第二次依然被驳回，把问题标成未解决上报，并让 `/no-comments` 判定失败。
3. 琐碎的采纳标记直接动手修掉，比如删掉死分支、去掉无用参数，或者改调真正的 API。只要有任何修复需要调整代码形态，就针对所有已采纳的标记连同周边代码跑一次 `/architect`，停在草图阶段即可。`architect` 负责定型，第 4 步负责实现。
4. 在范围内落最小根因修复，把点名出来的每一处绕过补丁清干净。如果根因落在范围之外，先在范围内落最小修复，把范围外的部分列成未解决事项上报。**principle-fix-root-causes** 和 **principle-redesign-from-first-principles** `skill` 只用来把握意图，两者都绝不授权扩大改动范围或去修范围外的其他实例。绝不要往上打治标防御补丁。
5. 约束类注释通常写着 `do not remove`、`do not change wording` 或 `talk to X before changing`。针对我们改不了的外部限制的保留项维持原样。其余的，给出范围内成本最低的结构化固化方案（类型约束、运行时检查、测试或 CI lint）。交互式会话里等用户批准；无人值守和 `eval` 模式必须有调用方事前授权。批准后先编码固化再删注释；未获批准则删掉注释、把这条未受保护的约束报成未解决，并勾勒出范围外需要补做的活。
6. 最终汇报：删掉了多少条注释、恢复了哪些注释、重跑次数、`architect` 草图、实际落地的修复、提出的编码固化建议、已落地的编码固化、仍未受保护的约束，以及其他未了结事项。
