# Sequence work into verifiable units

把工作排成一串小单元，每个单元都以可验证的状态收尾，当前单元没变绿之前绝不往下走。

**为什么这么做。** 在刚改完的那个小单元里抓到破损，定位几乎零成本。攒完一整批才发现坏了，问题早就被埋深了，而且你已经在坏底座上又盖了好几层。把同样这批小单元按顺序编排成评审人能逐个回放的交付链，就能把「信我没错」变成「你看它先红后绿」。

**执行阶段。** 做全库清扫、迁移或任何一批同类修改时，每改完一个单元就立刻验证，再开下一个。每个单元都像一对前后括号，从已知完好状态出发，做一处改动，跑完检查，再往前走。开工前先 rebase 到干净的主干分支上，确保每次检查都在拿真实基线对照。哪怕修改本身是靠脚本杠杆跑的，逐单元检查几乎零成本，也照跑不误。

**交付阶段。** 按能自证清白的顺序叠放 commit 和 PR。最经典的排法是先放复现失败的测试，再把修复叠在上面。其他常见的叙事顺序还有先删旧包袱再重塑结构、先抓基线再上优化、先搭脚手架再落功能。每个 commit 都能独立站住，整串顺序读下来就是一份完整的论证。

这条原则在执行顺序上与 **prove-it-works** `principle` `skill`（保证每次检查都测真实对象）和 **build-the-lever** `principle` `skill`（把逐单元检查成本压到极低）互为补充。
