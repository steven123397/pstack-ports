### Autopilot-full

**判定结论归你把关，PR 本身交给主理代理。每个 PR 由一名主理代理（`owner`）从开发一路带到合入，但在你那组从未写过这段代码的验证 `swarm` 证明即将落地的代码无误之前，任何东西都不准合并。**

一份判定只覆盖对应的那份补丁，全绿 CI 只覆盖对应的那个 head。第 4 步只跑一次完整 `swarm`，只有在出现重大改动时才重跑整组。`playbooks/shipping.md` 里的 `patch-id` 规则可以延续未变通道的结果，但每个新 head 仍须拿到自己的全绿 CI。

1. **操作者划定的卡点优先级最高。** 全自动授权只覆盖本队列内的事项，凡是操作者点名归他自己管的项以及队列之外的 PR，一律走到已就绪可合入就停手。用户让你先汇报计划，绝不等于已经放行开干。
2. **每个 PR 派一名主理代理，并把它的进度留在接替者找得到的地方。** 整项任务开头一次性判定代码托管平台：默认 GitHub CLI（`gh`）；如果 `command -v origin` 成功且 Origin 能解析当前仓库，所有 PR 操作一律用 `origin pr`，否则留在 `gh` 并记录回退，绝不依赖 Graphite（`gt`）。每名主理代理都是一个 Cursor 云端代理，负责写代码、按 `playbooks/opening-a-pr.md` 开 PR、在真实产物上自证效果、按 `playbooks/babysit.md` 盯盘跑绿，等第 4 步和第 5 步放行后自行合入。

   PR 要早点开出来，好让 CI 和机器人同步跟着跑。只有先过完 `cursor-team-kit` 里的 `/deslop` 清理和 `/no-comments` 审查，才算代码就绪（code-ready），这样完整验证 `swarm` 跑在的是成品代码上。接着 rebase 到最新主干，在自证之前先上报 code-ready head，确保验证跑在真正要落地的基线上。之后每次有新 head 都要上报，等自证、CI 和 `Babysit` 全过后再报 merge-ready。修 review 或修 bug 的轮次尽量留在同一个 base 上，除非主干冲突、把 CI 弄红，或有人往相同文件合入了已知并发改动，因为每次 rebase 都会重启整套 CI。在推送 code-ready 以及后续需要重新验证的推送之前，务必在已提交的 head 上先跑完触及路径对应的仓库检查。

   时刻按「这台虚拟机随时会挂」来做事。开工后尽早推送分支，并按 **show-me-your-work** `skill` 在根代理的存储目录（路径见系统提示词）建好决策日志；之后每干完一个单元先 push 再开下一个。谁派生了子代理，就在存储里记下它的 id、状态以及同类代理历史上判定卡死的超时阈值（stuck-after runtime），万一父级挂了根代理还能继续探活。只允许对自己负责的分支做 force-push，且必须带 `--force-with-lease` 锁定到你上次推送或接手时的 SHA；一旦发现分支上有不是你推的提交，立刻停手向根代理汇报。
3. **各路主理代理全部基于主干并行开跑，绝不叠栈**，让每个 PR 都能独立落地。
4. **整组 `swarm` 只跑一次。** 完整 `swarm` 在 code-ready head 跑一次；只有新增行为、重新设计或大规模新 `diff` 时才重跑完整 `swarm`。普通 rebase、解合并冲突或微小修复只在新 head 上派单个验证代理复查；纯文案调整不派验证。在 code-ready SHA 上按 **swarm** `skill` 扇出独立验证代理：重跑所有门禁、通过对应的 control `skill`（如 `cursor-team-kit` 的 `control-ui` / `control-cli`）或指定驱动在真实运行端实跑核心行为，并审计 `diff`。缺少实跑通道，或者根代理还没核对完 merge-ready 报告里的所有实证回执之前，判定都不算干净，因为任何通道都不轻信自己没亲手查过的宣称。

   只有拿得出实证的问题才允许阻塞 PR，具体指在当前 head 上跑出失败结果，或 PR 把随包文档改错了。如果问题是 PR 底座（主干或栈里下面的 PR）本来就有的，不阻塞本 PR，除非本 PR 把它复制了一份或者新走到了这条坏路径。只有用户真会撞上的 bug、挂掉的门禁或写错的随包文档才阻塞，其余一律记成后续单。
5. **主理代理只合入经过你验证、且针对目标主干测过的代码。** 光有全绿 CI 绝不能当合并授权。验证 `swarm` 各通道启动后，合入准备阶段先 rebase 到最新主干、上报新 head，并等 CI 变绿。

   真正点合并前一刻，fetch 最新主干并判断主干的新改动会不会影响这份补丁，别为了主干每动一次就无休止地 rebase。只要即将落地的代码从未一起测过（比如有冲突、两边改了同一文件，或主干改了本 PR 要跑哪些检查），就必须 rebase 并等 CI 变绿。如果两边都动了 lockfile，只要在合并结果上跑 frozen install 通过、且本 PR 改动的包解析结果与 head 一致，就不需要重 rebase（这次安装已经验了将要落地的 lockfile；如果安装挂了就必须 rebase 修好）。如果主干改了本补丁的调用方或本补丁依赖的对象（被调用代码或依赖版本），在合并结果上跑完补丁对应的检查，通过就直接合入；其余情况直接合入。如果合入准备之后主干又逼出第三次 rebase，立刻暂停上报给根代理，由根代理把互相撞车的工作排成串行顺序。
6. **守好根控层。** 任何会放宽门禁的改动（比如调高预算上限、加白名单条目），必须先由验证代理证明合理，再由你给出新的会签批准（countersign），因为主理代理天然偏心想让检查变绿。在涵盖审批权限的授权下，这份会签就是批准，主理代理的记录里要指向你的会签供检查通道核验。直接禁用检查或把失败改成软失败（soft-fail）一律砍掉，因为它会让所有场景都失去保护。绝不代批或绕过托管平台本身强制要求的人工审批，任何会签都不能越过它。

   操作者放行后，挂上 `/loop 1h` 持续审计直到所有委派任务清零，因为长跑任务必会漂移、代理也会静默卡死。每一次 tick 先从主干重读本 `playbook` 并当场修掉记录漂移（例如漏报的 head 或没登记的代理，让对应主理代理补记），因为漂移是台账缺口，不算代理卡死。逐层探查每个代理直到最末端的通道，只凭实际副作用判断进度，不信状态文案和口头摘要。代理报错、起不了新轮次、超过 stuck-after 阈值没有任何新动静，或者主理代理到第一个 tick 还没推过代码也没写过一行日志，都算卡死。停着等你或操作者回复的不算卡死，直接回复它推进即可。发现卡死立刻派替代代理接盘，不等旧代理的停止指令落定。凡是本轮 tick 出现了操作者关心的新变化，结尾按 **ketchup** `skill` 同步一次；什么都没变就保持安静。
7. **操作者喊停立刻全员收手。** 暂停指令作为「零写入命令」传达到每名主理代理。各自汇报当前落脚点并保留手里的 `brief`，等待操作者解除暂停。

**Reply：** 按 **ketchup** `skill` 向操作者同步全局，涵盖每个 PR 的状态与判定、已合入项、会签批准及理由、仍开着的操作者卡点以及挂起的后续单，并附上所有 PR 和决策日志的链接。
