### Multi-phase or multi-PR plan

**计划文档归你把关，业务代码不归你写。这份计划是一张勾选清单，供主理代理逐格推进、供操作者凭证据审计。** 交付物就是计划本身，不要动手实现。

1. 如果改动只涉及一两个文件且做法一目了然，直接跳过计划，说明理由并停手。
2. 动笔写计划前，先按 `playbooks/prototype.md` 做原型解决开放问题。只把任何实跑都定不了的产品或偏好取舍留给操作者拍板。
3. 编写计划文件。开头写明要改什么、按合入顺序列出各 PR 编号，以及依赖关系图，说清哪些 PR 彼此独立直接从主干拉出、哪些要等哪些落地、每个 PR 允许动哪些文件。随后每个 PR 单独一节。一个 PR 只做一件事并自带独立证据（遵循 **sequence-verifiable-units** `principle`）。每一节都配齐勾选框：前置依赖、修改文件、本 PR 要建的这一项改动、可见结果，以及验证项。
4. 光跑测试不够当验证。只有当一个 PR 的单测（unit）、实跑（live）和性能（perf）勾选框全部打勾，才算验证通过。每个实跑框都要在真实运行端跑具体场景并写出通过判定；性能框要写明指标、探针、先测出的主干基线以及判定失败的阈值。涉及交互变更的 PR 在合入前必须等操作者审核确认。
5. 交回计划文件路径并停手。等操作者明确放行后再启动执行。

**Reply：** 计划文件路径、各 PR 编号及其依赖关系与需人工审核的集合，以及哪些点尚未得到证实。
