### Bug fix

**这项任务归你把关。负责规划、审查和验证。** 把排查和写修复派给子代理，你留在主控位带队。按 `Subagents` 一节给每个子代理挑好推理档位。

严格讲科学。合入的每一行代码都必须对应运行时证据。「加一道保险说不定有用」的防御写法只是猜测，不是修复，绝不允许合入。一旦证据推翻了某个假设，立刻回滚它引出的改动。只交付证据证明必需的最小改动，不多加一行。

1. 用对应的 control `skill`（见「铁律」）亲自在匹配的真实运行端上复现，哪怕某份调试或打点协议里写着让用户来复现也一样。只有当控制端确实触达不到目标、且你已经尽可能推进到极限后，才说明具体原因请用户协助复现。如果直接复现不出来，就人工构造触发条件、收紧约束或加打点，直到把它稳定复现出来。
2. 二分排查根因。列出候选假设，逐个排除直到只剩唯一真因。结合对受影响子系统的代码追踪以及 **why** `skill` 查出的回归历史来提出假设。每一轮都挑最能砍掉一半以上排查空间的切分点，拿运行时证据，淘汰错误分支。程序状态看不清时，加打点或日志边跑边读，别靠猜。遇到耗时或顽固的排查，挂上 Cursor 的 `/loop` 命令持续推进。必须先拿运行时证据坐实幸存的*作用机制*，再进入第 3 步的 `architect` 或 `interrogate` 扇出。
3. 规划修复方案。如果改动跨越函数边界，先走 `architect`。然后用配置好的 `bug-fix` 模型（默认 `claude-opus-5-5-xhigh-fast`）把实现派给子代理，并划清具体范围。
4. 在同一个真实运行端上复验。原先的复现步骤现在必须通过。报「结论未定（inconclusive）」或测错了端，一律不算通过，必须标出来。单元测试只证明某个分支逻辑，不代表真实 bug 已经消失。
5. 组织 commit 顺序，让「能复现失败的测试/用例」在 git 历史里落在修复提交之前。如果这个 bug 有便宜好跑的本地测试路径，按 **tdd** `skill` 走先红后绿节奏；如果测试太贵、集成太重或路径不清，就跳过。这是 **sequence-verifiable-units** `principle` 的标准落法，失败用例在前，修复叠在上面。
6. 收尾执行 **Opening a PR**。

**Reply：** 哪里坏了、根因是什么、怎么修的、怎么验证的。把先失败后通过的复现输出原样贴出来。
