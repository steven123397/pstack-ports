# TDD Bug Fix

修一个具备清晰、低成本测试路径的 bug 时，先在动生产代码之前把故障行为做成可执行的失败测试。目标是落下一条聚焦的回归测试，修之前必挂，修之后必过。

条件不合适时绝不要硬凑测试。如果能写的测试需要搭庞大的测试 `harness`、写脆弱的 mock、依赖慢吞吞的端到端基础设施、依赖线上专有状态、复现步骤本身就含糊，或者会搅动一大片无关测试夹具，就跳过新增测试，改用最贴近实战的有效验证方式。

## 工作流

1. **吃透这个 bug。** 理清预期行为、当前实际行为、受影响的代码路径，以及最小可观察复现条件。
2. **挑最窄的可执行检查。** 优先复用这条代码路径原本就在用的最近一层单元、组件、集成或回归测试。如果根本没有顺手的测试入口，别为了走流程硬从零造一套测试体系。
3. **先写失败测试。** 补一条最小、最聚焦的测试，确保它本来就能拦住这个 bug。测试要编码预期行为，不要去照镜子式地绑定当前实现。
4. **修代码前先跑新测试。** 确认它确实因为预期中的那个 bug 挂掉。如果它居然直接过了，或者因为八竿子打不着的原因挂了，先调好测试或复现条件，再碰业务实现。
5. **修复 bug。** 做能满足预期行为的最小生产代码改动，同时保住周边原有契约不被破坏。
6. **重跑回归测试。** 确认这条测试现在稳定通过。

## 当写失败测试不现实时

改用最接近的可执行回归检查，比如定向验证脚本、手工复现命令、浏览器自动化操作、快照比对、日志断言或聚焦的集成检查。

宁可不加新测试，也别写烂测试。所谓烂测试，就是大部分时间都在测 mock、绑死当前实现细节、依赖脆弱时序或无关全局状态、为了一个小修补非要拉起昂贵基础设施，或者证明完修复就恨不得立刻删掉的测试。

## 护栏

- 绝不要为了迎合错误实现去改测试。
- 除非预期行为确实变了且理由明确，否则绝不要放宽已有断言。
- 回归测试只盯住当前 bug，避免顺手大改无关测试夹具或盲目扩充无关覆盖率。
- 如果 bug 时隐时现、带随机性，尽可能把测试做成确定性的，并写清锁定的具体信号是什么。
- 如果这个 bug 暴露了一整类同类问题，先把当前聚焦的回归路径落地，再考虑补齐同类兄弟用例。

## 最终汇报

交出证据，别光报一个「修好了」的结果：

- 点名修复前跑挂的测试或可执行检查，以及它当时报出的具体失败信息。
- 点名修复后跑通的测试运行记录，以及顺带跑过的周边验证。
- 如果实在没法演示「修复前必挂」的证据，如实说明原因，并写清改用了哪项最接近的回归检查。
