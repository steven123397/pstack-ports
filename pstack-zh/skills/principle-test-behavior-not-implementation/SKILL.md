# Test Behavior, Not Implementation

测试是对代码为其使用方提供什么能力的一份声明，使用方可以是调用方、终端用户或其他服务。所谓行为，就是这些使用方通过他们所用的接口能观察到的一切，包括返回值、抛出的错误、能回读到的状态，以及对代码外部系统产生的影响（比如发出去的请求、写进库的行、发出的消息）。所谓实现，则是他们看不到的东西，比如私有辅助函数、内部调用顺序、中间数据，以及内部到底派了哪个协作者去干活。

用两次假想改动来检验每一条测试：

- **搞坏行为。** 让代码返回错值、漏掉一次副作用，或者把副作用执行两遍。如果测试居然还能过，它就什么都没证明。常见毛病包括断言写得比契约宽松、拿被测代码自己算出来的东西当期望值、直接复述一个常量或 `prompt` 字符串却从没跑过读它的代码，以及对着测试自己造出来的假数据做断言。
- **改掉内部实现。** 保持所有外部可观察结果不变，把底层代码重新组织一遍。如果测试这时挂了，说明它绑死了内部实现。这种测试每次重构都得重写，真出 bug 时却拦不住。

能抓出第一种改动、又扛得住第二种改动的测试，才值得留下来；其余的一律重写或删掉。要写出两头都达标的测试，就拿具体输入从使用方的对外接口驱动代码。期望值必须从需求本身推出来，别拿跑一遍代码吐出来的结果凑数。契约承诺了什么就断言什么，不多也不少。

划定边界靠的是契约本身，不是断言长什么样。如果契约承诺「空购物车绝不扣款」，那断言支付客户端一次都没被调用，测的就是行为。同时要配一个真正发生扣款的用例，证明这条测试确实能观测到调用。被 mock 的外部服务收到的请求载荷属于行为，因为那个外部服务真会看到它；对内部辅助函数的调用属于实现，因为没有任何使用方看得到。没有匹配记录时，空列表就是精确答案；但如果测试本来只需要「有结果就行」，拿非空当断言就太空洞了。死磕精确报错文案会把没人读取的措辞焊死，调用方拿来做分支判断的错误类型才是契约。

测试也可以钉住一个不变量，而不是某次具体调用，比如某个键必须同时存在于两张表里，或者一项编译期类型检查。不变量本身就是行为。
