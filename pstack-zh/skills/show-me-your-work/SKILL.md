# Show me your work

全程只维护一份权威日志。

## 格式规范

单个 TSV 文件，每条决策占一行。每个单元格严格单行。证据栏只放指向真实产物的指针，不写大段散文。

拷贝 `references/decision-log-template.tsv`（表头行）起一份干净的新日志。字段定义如下：

- **ts。** ISO8601 时间戳。
- **phase。** 当前阶段或工作流分支。
- **decision。** 选了什么或干了什么，一句话写完。
- **why。** 用大白话写明原因。如果是某条 `principle` 驱动的，直接说人话，别只贴个术语标签。
- **evidence。** 能证明结论的链接或路径，比如 commit SHA、PR 号、`file:line`，或产物、trace、截图路径。绝不写一段话。
- **result。** 实际结果或判定状态，例如 `tests green`、`reverted`、`pixel-diff 0`、`INCONCLUSIVE`、`open`。

示范如下，全用大白话写，评审人扫一眼就能看懂：

```
ts	phase	decision	why	evidence	result
2026-05-24T09:02:00Z	frame	先盘清工作量，约 100 个组件、粗估 75 小时	开跑长任务前先摸清体量	commit 3a9f1c2	开工前发现 5 处待理清问题
2026-05-24T09:40:00Z	harness	动代码前先给旧版全量截基线图	方便后面逐像素对比抓出视觉偏移	scripts/snapshot.sh, baseline/	存下 120 张基线参考图
2026-05-24T11:15:00Z	widget	迁移组件样式但不改变外观	保持改动小且视觉零差异	commit 7c21e0a, pixel-diff 0	视觉一致，测试全绿
2026-05-24T12:30:00Z	widget	废弃一个辅助代理的产出，因为它截的图全是白屏	直接查了真实文件，没轻信它的汇报摘要	worktree reset	已回退，收紧了下一轮指令
```

## 追加日志行

每一条记录都按当面给同事交代工作的口吻写。用直白话和具体动作，不带 AI 腔和抽象黑话（**unslop** `skill` 同样管日志正文）。

使用辅助脚本 `scripts/log.sh <logfile> <phase> <decision> <why> <evidence> <result>`。它会自动打上 `ts`、首次写入时补表头、清理混入的制表符和换行，并给以 `=`、`+`、`-` 或 `@` 开头的单元格加上单引号前缀防公式注入。用裸 `printf` 追加也可以，但如果单元格内容来自程序生成或外部输入，必须同样做好上述字符防护。

只记决策点和检查点，别把每一步琐碎操作都记进去：选定分支路线、单个单元完工及其验证结果、转向或回退及其触发原因、暴露出的阻塞项、修好的门禁。循环类任务每轮迭代记一行。显而易见的琐事跳过。

一次「运行（run）」指单个代理会话，包括它后续的多轮对话和上下文压缩摘要。断点续接、换新代理或开新对话都算新的一次运行。当一次运行往已有记录的日志里追加内容时，它的第一行必须用 `phase` 值 `start`；在其他运行插了 `start` 行之后再回来写，第一行同样要写 `start`。因此，同一运行在后续轮次回到日志时，先读最后几行确认中间有没有别的运行写过。`start` 行要标出它前面那些非本运行写入记录的 `ts` 区间，并在 `evidence` 栏写明本次运行标识（如代理 ID）。除了标记新运行起点，`phase` 值 `start` 绝不用于其他用途。

## 存放位置

默认情况下，日志只是工作过程产物，不提交进 Git。放在工作目录的 `decisions.tsv`；多条任务并行时放在 `.audit/<task-slug>.tsv`，留在 Git 之外。

只有当这项工作足够庞大复杂、评审人必须靠完整轨迹才能放心信任结果时，才把它提交进仓库。

## 硬规则

- 只追加不修改。判断错了就新追加一行来覆写说明，绝不要回头改写或删掉历史行。
- 优先引用已提交脚本产出的证据，而不是一次性的手工排查（参见 **encode-lessons-in-structure** `principle` `skill`）。

## 对照对话记录审计日志

本次运行收尾交差前，核对日志说的是不是全都是实话。读取当前活跃工作区 `agent-transcripts/` 目录下本次运行的 transcript（系统提示词里写明了该路径），绝不要用通配符横扫 `~/.cursor/projects/*/`，那样会越过工作区边界读到无关项目的私密对话。逐段核对本次运行写下的所有行是否和实际发生的一致。每一段起点是本次运行的某条 `start` 行（若日志由本次运行新建，则从第一行算起），终点到下一次其他运行的 `start` 行前：

- 核对每一行都对应一次真实发生过的决策或动作。
- 核对每一行的证据指针真实存在，且内容与该行声称的一致。
- 凡是实际影响了走向的分叉、转向或放弃路线却没写进日志的，都算漏记，补追加进去。

只修日志，绝不篡改历史。审计绝不编辑或删除任何已有行，哪怕发现某一行是凭空编的也一样。如果某一行既不对应真实决策也不对应真实动作，或者结论与证据有误，就新追加一行覆写它，写明真实发生了什么并附上能打开的证据指针。本次审计不核查非本次运行区间里的旧行；但如果本次运行的工作顺带证伪了某条旧行，就按普通错误决策追加一行覆写。

## 跨模型复核审计轨迹

正式交差前，派一个与干活主模型不同模型家族的子代理做复核。自己审自己不算数。这位复核子代理通读审计轨迹和本次运行的 transcript，标出用户真正该留神的地方。它不是把活重干一遍，而是专门扫出不够妥当或暗藏风险的环节。按 **poteto-mode** `skill` 的 Subagents 章节，为子代理选定匹配的推理档位与 fast/standard 速度。重点扫四类问题：

- 记进了日志但证据薄弱或缺失的决策。
- 被跳过、或在 transcript 里找不到实证支撑的验证步骤。
- 事后复盘显得冒进的选择（过早拍板、范围蔓延、只掩盖表面症状）。
- 人类扫一眼 diff 很容易漏掉的死角。

凡是产出了决策轨迹的运行，最终回复末尾都必须带一个「Attention」小节。首行独占一行写明复核模型（`reviewed by <model>`），接着逐条列出指向具体日志行或对话时刻的提醒。没有任何问题时写「No flags」完全合法，但绝不能省略或伪造模型名。

## 如何查阅轨迹

从上往下通读，顺着证据指针抽查核对。提交到 GitHub 的 TSV 会自动渲染成表格；在终端里可以用 `column -s$'\t' -t decisions.tsv` 对齐查看。

## 供其他 `skill` 组合调用

其他需要留审计轨迹的 `skill` 直接把记录路由到这里，别各自重造一套格式。直接点名引用本 `skill`，把表头和格式规范完全交给本 `skill` 管，不要在其他文件里重复抄写字段定义。
