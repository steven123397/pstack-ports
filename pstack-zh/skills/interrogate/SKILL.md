# Interrogate

让对抗评审代理专门去把改动或设计跑崩。查出的问题（`finding`）只有靠真实运行证出来才作数。只汇报查出的问题，不要动手改代码。

## 定框

范围按用户点名的为准；没点名时，默认取当前分支从与基线分支的 merge base 到当前工作区的完整 diff。先用 **in-your-own-words** `skill`，根据用户消息、commit 历史和 PR 描述把改动意图复述清楚。意图模糊就直接问用户。

## 并行扇出

按 **arena** `skill` 的 Phase A 第 3、4 步和 Phase B 执行，但做四处调整：模型列表改读 `interrogate reviewers` 行而不是 `arena runners` 行；把范围内未提交的工作区改动一并拷贝进每个 `worktree`；每个对抗评审代理都以 `generalPurpose` 身份启动；不发 `arena` 的任务和设计缘由要求，改成把范围、意图和下面这份 `brief` 交给它们：

> 想办法把这次改动跑崩。每一条查出的问题，都必须拿对着真实代码跑出来的证据证明，比如一条挂掉的测试、一个复现脚本，或者直接显示错误行为的命令输出。面对设计稿或计划书，就跑一个原型或在当前代码树里实测探查。复现脚本留在你自己的 `worktree` 里。每条问题必须写清标题、确切命令、实际打印的输出，以及原定意图要求的正确输出。没实际跑过的东西一律别报，包括代码风格、命名、结构偏好，以及得等以后再改代码才会出事的假设性风险。一条没查出来也是完全合法的结果。

## 复核验证

按 `arena` Phase F，把每条查出的问题对应的命令重新跑一遍核实。只有当输出确实暴露了故障、且该故障确实违背了原定意图时，才保留这条 `finding`；其余全部剔除。共享同一个根因的问题合并成一条。

跳过 `arena` 的 Phase C、D、E。不同对抗评审代理能抓出不同的真实故障，所以最终结论要汇总保留每一条经实跑复核成立的 `finding`，而不是只选某一个代理的清单。

## 输出格式

- **意图（Intent）：** 前面复述的改动意图。
- **查出的问题（Findings）：** 列出每一条复核通过的 `finding`，附确切命令、实际输出、它如何违背了原定意图，以及是哪几位对抗评审代理查出来的。如果全军覆没一条都没留下来，直接写「无经实证成立的问题」。
- **已剔除项（Dropped）：** 按对抗评审代理分别列出被剔除的条数及剔除原因。
