# Technical writing

把文档写到让一个已经很累的工程师第一遍就能读懂。下面四层标准叠加使用。

有三条总原则凌驾在四层之上：

- **删掉每一个不干活的词。** 如果删掉某个词后句子照样成立，就删掉它。英文里的 `"In order to"` 改成 `"to"`，`"It is important to note that"` 直接删光；中文里的「为了能够」「值得注意的是」同理。
- **优先用短小的日常词。** 英文用 `"Use"` 不用 `"utilize"`，用 `"Help"` 不用 `"facilitate"`，用 `"Do"` 不用 `"perform"`。一个长词必须靠精确度赚回它的长度。
- **当某条死规则把句子改难看了，换种写法修句子，或者干脆别硬套。** 一句条条守规矩、读起来却像机器拼出来的句子，就是失败的句子。

代码库本身就是词表。直接写真实的符号名、文件名、参数标志或命令名，别给它编同义词或绕弯描述它。

别自造黑话。用开发者嘴里真会说的话，比如「移动」「删除」「只降不升的预算上限」，别写 `evacuate`、`ratchet`、`endgame` 这类虚词。只要文档首次出现时讲清楚含义，公认的命名模式可以用。如果你发现新的抽象隐喻词，在回复里提议把它和直白替换词补充进 `unslop` 的抽象隐喻规则并附上 diff，但不要直接去改那个 `skill`。

## 调节句式节奏

一份文档完全可能每层规则都遵守了，读起来却还是像机器写的：每句都切得一样短、全篇没有观点、没有具体落点。

- 有意识地长短句搭配。短句用来定调砸实，长句用来交代带条件或后果的完整事实。
- 「一句只说一个意思」不等于「每句长度都一样」。一条承载两个意思的句子要拆开；一条只表达一个完整意思的长句可以保留。
- 在文体允许的地方亮明观点。解释型文档本来就在权衡取舍，直接说出你的判断，别光机械罗列优缺点；参考手册则保持冷静客观。
- 写具体事实，不写无菌套话。别写「schema 变更可能引发问题」，要写「重命名列会让构建直接失败」。

## 第一层：先定文档模式（Diátaxis）

一篇文档只承担一种模式。用两个问题定模式：内容服务于动手（操作）还是理解（思考）？服务于学习还是干活？

- 动手 + 学习：**教程（tutorial）**。
- 动手 + 干活：**操作指南（how-to）**。
- 理解 + 干活：**参考手册（reference）**。
- 理解 + 学习：**原理解释（explanation）**。

这个罗盘既能拿来定整篇文档，也能拿来检视单句话。

**教程（Tutorial）：在做中学。** 让学习者跑通是你的责任，不是他们的责任。开篇直接说读者会亲手搭出什么，别说他们会「学到」什么。每一步都尽快给出肉眼可见的结果，告诉他们应该看到什么，比如预期输出、提示符变化或日志行。原理说明压成半句话再给链接。全程具体落点，用「我们」和祈使句带着走：「先做 x，现在做 y。」

**操作指南（How-to）：直奔目标的步骤。** 解决人真会碰到的实际问题，不是罗列机器具备的功能按钮。默认读者已经有基础，跳过教学。只写动作，不跑题、不讲背景故事、不为了大而全硬凑内容，需要背景就放链接。允许分支和条件判断：「如果你要 x，就做 y。」标题直接按任务起名，写「如何校准雷达阵列」，别写「雷达阵列校准」。

**参考手册（Reference）：供速查的事实。** 只做客观描述，不写操作教学、不劝说、不夹带私货观点。干脆、完整、笃定，直接陈述事实、选项、上限和报错，不留模棱两可的余地。文档结构尽量镜像代码结构，方便读者对照查阅。把信息放在读者预期能找到的地方，能从代码自动生成就自动生成。

**原理解释（Explanation）：讲透来龙去脉。** 聚焦一个边界清晰的主题，脱离产品界面也能独立读懂。每个标题前面都可以隐含加上「关于……」而通顺。锚定在一个真实的「为什么」问题上，讲清设计决策、演进历史、外部约束和备选方案。只有这一类文档允许表达观点，其他三类都不行。

绝不要混搭模式：教程里不塞参考速查表，参考手册里不手把手教学，操作指南里不长篇辩论。该拆就拆，互相用链接串起来。

## 第二层：直接对着读者写句子（Google 开发者文风）

- 用第二人称「你」和现在时跟读者说话。只有确实发生在后面的事才用将来时（`"will"`）。
- 说清是谁干了什么：写「编译器校验查询」，别写「查询被校验」。只有在动作发出者未知或无关紧要时才用被动语态。
- 操作步骤一律写直接祈使句（「点击 Submit」），事实直接平铺直叙，绝不写「应当被执行」。
- 条件放前面，动作放后面：「要删除文档，点击 Delete。」
- 常见情况放前面，例外情况放后面。
- 语气像一位懂行的朋友。不堆流行词、不玩修辞比喻、操作步骤里不写「请」，也绝不在流程里写「只需」「很简单」「快速」。要是真这么简单，读者根本不会来翻文档。
- 别画饼预告（「我们很快将支持……」），也别让连续几句话用同一个开头起句。
- 链接文字必须说清点进去是什么，用目标页标题或简短描述，绝不写「点击这里」。能在本页用一句话讲清背景，就别把读者赶去点外链。
- 标题要直接亮观点，别只贴一个光秃秃的主题标签（写「先定文档模式」，别写「模式」）。英文标题用句首大写（sentence case）。任务型标题用动词短语（「Create an instance」），概念型标题用名词短语。每页只有一个 H1，不跳级。
- 有先后顺序用有序列表，其余一律用无序列表。列表前用完整句子引出，列表项保持语法结构平行。
- 代码用行内代码字体，UI 控件名加粗。英文并列保留牛津逗号（serial comma）。去掉「等等 / etc.」，如果列表不完整，直接在开头说明这只是部分列举。

## 第三层：让句子一次只装一件事（STE 规则）

- 一条操作指令占一句；其余正文也是一句话只装一个意思。
- 英文操作指令超过约 20 词、普通句子超过约 25 词就拆句；中文同理，一口气读不完的长句就拆成短句。
- 警告和前提条件必须放在它所保护的步骤之前：「如果热油溅到皮肤上，会造成烫伤。」
- 写英文时保留冠词 `"the"` 和 `"a"`：`"Remove backup file"` 有两种读法，`"Remove the backup file"` 只有一种。
- 一个词只给它一种含义和一种词性，从一而终。如果 `"check"` 用来表示「检查」，就别在别处拿它表示「抑制」。
- 同一个动作只选一个词并坚持到底：用了 `"start"` 就一直用 `"start"`，别这儿写 `"start"` 那儿换成 `"initiate"`。
- 流程步骤写成直接命令，绝不写成旁白叙述，也绝不用被动语态：写 `"Install the component"`，别写 `"the component must be installed"`。
- 写英文时尽量少用 `"-ing"` 分词结构。

## 第四层：绝不给句子留出两种读法（全球英语 Global English）

- 写英文时，把 `"only"`、`"not"` 这类限定词紧贴着它修饰的词放：`"only fails on growth"` 和 `"fails only on growth"` 意思完全不同。
- 拆散超长名词串：`"the proto import budget check script"` 拆成 `"the script that checks the proto-import budget"`；中文里避免一连串「的」字定语堆叠。
- 确保每个「它」「它们」「这」（`"it"`、`"they"`、`"this"`）都明确指向唯一对象。拿不准就重复名词。绝不要用 `"this"` 或 `"which"` 去模糊指代前面一整句从句。
- 别省掉动词：`"Phase 1 moves the converters and Phase 2 the runtime"` 让 Phase 2 丢了动词，把动词补全。
- 保留标明句子结构的小词，比如 `"Ensure that the switch is off"` 里的 `"that"`。绝不为了省一两个字牺牲清晰度。
- 并列项可能引发误解时重复冠词：两个独立对象写 `"the client and the host"`，别写 `"the client and host"`。
- 当 `"and"` 或 `"or"` 连接的范围可能出现两种断法时，把分组写死。`"Both...and"`、`"either...or"` 和 `"if...then"` 是零成本的消歧利器。
- 用句号，别用分号。把长破折号换成另起一句。
- 括号里的文字要么本身是完整语法单元，要么干脆独立成句。写英文绝不用 `"(s)"` 凑复数。
- 别用斜杠偷懒：写 `"a, b, or both"`（或「a、b 或两者」），别写 `"a/b"` 或 `"and/or"`。
- 同一件事从头到尾只叫同一个名字。一份文档把同一个东西轮流叫成「门禁」「棘轮」「预算检查」，读者就会以为这是三样东西。没变的东西就别换叫法。
- 避开习语、俚语、拉丁缩写和隐喻。

## 语调与仓库约定

- 凡是本 `skill` 经手的每一份文档，都要过一遍 **unslop** `skill`。AI 腔词汇、凑字废话、过度叠甲和格式破绽清单全归它管。
- PR 描述和 commit 信息同样算技术写作，除了 Diátaxis 之外的所有层级都适用。PR 正文应该是一份评审人一分钟内就能读完的简报，别往里面贴大段 `swarm` 日志、SHA 清单或指标大表，放链接即可。
- 产品界面文案不属于技术文档，界面文案走产品自己的文案规范。
- 代码片段用 Tab 缩进。写仓库里的真实路径。文档里写的每一处数量统计或目录树声明，在合入的那条 commit 上都必须真实有效，并附上重新生成它的命令。
