# Statechart

这张状态图用读者的日常语言展示系统如何在各个状态之间流转。由读图的人来拍板这套行为到底对不对。

## 运行方式

在仓库目录之外的临时文件夹里干活。写好一份 TLA+ 规约和它的配置文件，然后运行：

```sh
<skill dir>/scripts/statechart SPEC.tla [--config FILE] [--view FILE] [--out DIR]
```

`scripts/statechart.ts` 是 TypeScript 脚本，请用支持直接执行 TypeScript 的运行时来跑。`scripts/statechart` 是自动挑选运行时的 POSIX shell 脚本。在原生 Windows 下，请使用 Node 22.18 至 22.x，或 Node 23.6 及以上版本，直接运行 `node --disable-warning=ExperimentalWarning <skill dir>/scripts/statechart.ts`。

首次运行会通过 mise 自动安装 TLC 和 Java，需要联网。

## 编写 TLA+ 规约

- 把读者认可的每一条业务规则写成一条 `INVARIANT`。规则可以约束页面显示、返回结果、落盘值或发出的消息。如果模型里还没有对应这条规则的变量，补上变量。绝不要为了凑通过去削弱规则。
- 把 `Next` 写成各个动作的析取，例如 `YouPressPlay \/ YouPressStop`。不这么写的话，TLC 会把每一步都统一叫成 `Next`。
- 没有任何出边的状态会触发 `NoDeadlock` 违规，哪怕它是一个正常的终态。当规约里已经有同名 `INVARIANT` 或 `PROPERTY` 时，死锁规则改名为 `CHECK_DEADLOCK`。往 `Next` 里补一个只在终态为真且什么都不改的动作，比如 `Done == phase \in {"paid", "failed"} /\ UNCHANGED vars`，并在 `step()` 里给它配个标签。

## 设计视图与画图

真正需要判断力的活归你来做，包括每个状态和箭头上怎么写人话、怎么分阶段配色、图表标题，以及交给读者的报告。把这些映射写进一个 view 模块，通过 `--view` 传进去。

为了让图里显示读者的语言，view 模块导出 `state(vars)`。`state()` 的返回值类型决定了状态图的形态：

- 返回字符串，画扁平状态图：`export const state = (v) => (v.paid ? "Paid" : "Paying");`
- 返回数组，画带父状态的嵌套图：`export const state = (v) => v.main.split(".");`
- 返回对象，每个键画一个并行区域（parallel region）：`export const state = (v) => ({ Playback: v.playback, Volume: v.volume });`

状态标签只写读者看得到或关心的事，比如「Paying」或「Lease held, write pending」，别把模型变量名塞进标签。在 `vars` 里，TLA+ 序列（sequence）是从 1 开始编键的对象（所以 `v.pc[1]` 对应 `pc[1]`），集合（set）则是数组。

view 模块还可以导出 `step(action, from, to)`，接收 TLC 动作名以及这一步前后的变量值，返回箭头上的标签。每条步骤标签按用户眼里看到的样子写，比如「you press play」或「the connect fails」，别报代码函数名或 TLA+ 动作名。如果两个动作在图上的落点效果相同，给它们同一个标签，好让它们合并成同一条箭头。

如果某一步只在特定条件下才能发生，在标签末尾用方括号按读者语言写明条件，比如 `you press play [while the file loads]`。在并行区域图（regions chart）里，脚本会自动在箭头上标注其他区域的条件标签（例如 `[when Offline]`）。你自己写的方括号会顶掉自动标注，可能导致同一个状态出发的两条箭头长得一模一样；因此在并行区域图里，不要手动用方括号写其他区域的条件。如果某个状态标签里没显示的内部值决定了这一步走向哪里，直接把结果写进箭头标签，比如「the roster read fails」。

view 模块还可以导出以下三个可选字段：

- `group(vars)` 返回阶段名，图上每个状态会涂上它所属分组的颜色。如果合并到同一个图状态底下的多个模型状态属于不同分组，该图状态就不着色。
- `colors` 为每个分组名指定一个颜色类名。
- `title` 是显示在图表顶部的标题字符串。

脚本对每个模型状态最多调一次 `state()` 和 `group()`，对每一步最多调一次 `step()`，图表和报告共用同一套返回值。因此每个函数都必须是纯函数，只依赖入参。

停留在同一个状态标签内的自环步骤不会被画出来。如果读者必须看到这一步，就把状态标签拆细。

尽量把总箭头数压在 20 条以内，再密就难读了。第一步先让 `state()` 返回更粗颗粒度的标签，把表现一致的值合并成同一个标签，省去读者不需要关心的内部细节（比如一个返回后什么也不改的在途请求）。但必须保留每条 bug 路径上的每一个状态以及每一个告警标记。合并一旦把 `breaks` 状态稀释成 `mayBreak`，就会遮住到底哪条规则在哪破了；也绝不要把违背不同规则的两个状态合到一起，否则读者分不清哪条规则坏在哪里。如果合并状态后图还是太密，在 `step()` 里对读者不需要看的步骤返回 `null`（比如每个状态都有的全局重置，或者和其他箭头重复的步骤）。隐藏步骤时必须遵守四条规则：

- 保证图上每个状态依然能从起始状态沿箭头到达。
- 凡是模型里原本有出边的图状态，图上至少保留一条出边。
- 要么把某条箭头对应的全部步骤一起隐藏，要么一个都不藏；只藏一半会让箭头条件悄悄变窄。
- 在交接说明里明说图上隐藏了哪些步骤。

## 读懂运行报告

- 图上必然违背规则的状态带 `breaks` 类；如果底层多个模型状态里只有一部分违背规则，带 `mayBreak` 类。图例（Legend）会列出每个标记对应的规则。当两条规则都破了时，图例会把两条规则标在同一个标记上，所以交接时要说清哪个状态破了哪条规则。在并行区域图里，只要包含某状态的每一种区域组合都可能违背规则，该状态就会被打标；如果某组合会违背规则但其中所有子状态都没单独打标，那么该组合里的每个状态都会被打标。
- TLC 碰到违背规则的状态后仍会继续探索，因此图里会画出 bug 发生之后还能走到的状态。
- 正因为 TLC 越过 bug 继续走，没有状态上限的模型可能永远跑不完。请把常量定小，或者加上 `CONSTRAINT`。
- 使用 `VIEW` 或 `SYMMETRY` 时，TLC 会把视为等价的多个状态合并计数成一个，图上也只画这一个代表状态。某条箭头可能会指向那个代表状态，而不是该步骤实际抵达的等价状态，报告里会注明这一点。
- TLC 会检查跨过 `CONSTRAINT` 或 `ACTION_CONSTRAINT` 之后抵达的那个状态是否违背规则，但不会继续向外展开它，也不会检查它的死锁。如果某条规则的最短反例路径正好停在这样一个越界状态上，图里会画出这个状态，报告也会给出该路径，其余越界状态则不画；这类状态上的死锁不会显示。TLC 同样会检查被 `ACTION_CONSTRAINT` 排除的步骤执行后的规则状态（哪怕目标状态还能通过其他路到达），如果最短反例以这样一步收尾，图里也会画出这一步。
- 脚本先按原样配置用单 worker 跑 TLC 检查全部规则。每当查出一条规则被违背，脚本就把那条规则移出配置再重跑 TLC，直到没有规则被违背为止。在发现第一条违规之后，后续每次运行会在 100,000 个独立状态处封顶停机，防止大模型无限跑下去。一旦某次运行触顶或报错中止，报告会在「Rules not checked」下把没检完的规则列出来，图上也不会给它们打标。没检完的规则可能成立也可能违背；想验证它们，先把已经破掉的规则从配置里移掉，或者把模型规模缩小。加状态上限时会引入一个改变 TLC 变量顺序的模块，因此对于 `PROPERTY`，TLC 找到的反例可能和无上限运行时不同。
- `tlc.out` 记录的是原样配置下 TLC 的原始输出。如果图上没画出某条违规规则的 bug 路径，`tlc-RULE.out` 保存的是抓出那条违规的那轮 TLC 输出。当 TLC 重复打印第一条警告时，裸跑 TLC 会印两遍，而 `tlc.out` 里只看得到一遍，因为 TLC 没把第二份放进本脚本读取的输出流。只有 Java 带 `-XX:+UseParallelGC` 运行时才会这样，否则 TLC 的第一条警告就是建议加这个参数（本来也只印一遍）。

## 展示状态图

把 `chart.mmd` 用 `mermaid` 代码块直接展示给用户。图表预算上限是原样配置下 TLC 算出的 500 个状态。超过 500 个状态时，图里只画通往违规规则的反例路径；如果一条规则都没破，脚本干脆不生成 `chart.mmd`，但它依然完成了所有规则检查，报告里会给出总状态数和每条 bug 路径。想看全图就把模型规模缩小。

统一用 Pele 渲染状态图。当用户要图片，或者图太大不适合直接看 Mermaid 文本时，按 `references/render.md` 渲染。除非用户明确要求，不要换其他渲染器。

## 交接汇报

把每张状态图连同它的 Mermaid 源码交给拍板的人。每个 bug 补一行说明，写明规则名、读者语言下的规则含义，以及报告里带编号的反例路径。老实交代模型省略了哪些东西。最后附上复跑整套产物的命令（换一个新的 `--out` 目录）。

如果模型描述的是真实代码，把每一条 bug 路径对着真实代码一步步重放成测试或现场复现，一个模型动作对应一步代码操作。如果真实代码里没复现出这个 bug，先假定是模型写错了，直到你能证明模型没错为止。
