# 设计缘由模板

随类型草图一并交付的文字说明。控制在一页以内。标题用平实短语，不写套话模板。把下面的斜体提示替换成真实内容。

## 问题背景

*写一段话。我们要解决什么问题，以及现有系统或外部约束里有哪些因素让架构形态并不显而易见。如果 [Phase A](../SKILL.md#phase-a摸底与定框) 挖出了设计必须遵守的硬约束（必须互通的既有类型、不能破坏的调用方、跨边界的不变量），全部点名写在这里，让读者看到和你一样的约束条件。*

## 用法（调用方视角）

*先写这一节，再画类型草图。展示使用方会读到的 README 或快速上手示例，再配两三个写在他们自己业务代码里的真实调用点，包括导入什么、怎么调、返回什么。[方案形态](#方案形态) 里的类型草图必须由这里倒推出来。两者必须严丝合缝，一旦出现出入，改草图去迁就用法，绝不反过来迁就。调用方的体验就是规格说明，类型是为它服务的。*

## 方案形态

*推荐的架构形态。先讲数据结构，再讲数据怎么顺着函数签名流动。点出起承重作用的关键决策。写明哪些不变量直接编进了类型、校验落在哪一层、以及系统刻意不去做什么。明确评价接口深度，说清对外接口面藏住了哪些复杂度、还有哪些留给了调用方，以及为什么这个接口已经精简到不能再小。每条决策顺手引用背后的 `principle`（例如「按 `boundary-discipline`」），不用重复解释原则内容。*

## 综合取舍结论

*由 [arena](../../arena/SKILL.md) 填写。记录最终选定哪份候选方案作为基底及原因、从其他各家分别手工吸取了哪些优点，以及拒绝了什么、为什么拒绝。*

## 接受的权衡

*选定方案所做的每一项权衡占一条要点，句式用「我们接受 X，以换取 Y」。把未来读者可能会误以为是疏漏的地方提前点出来，包括那些乍一看像过早优化或过度简化的取舍。*

## 评估过的备选方案

*必填。至少点名一个具体的备选架构形态，用一句话讲清它为什么落选。评价每个备选方案时要看接口深度，不能只看实现是不是简单，写清它把哪些复杂度露给了调用方、又藏住了哪些。如果设计空间里真有旗鼓相当的竞争对手，列两三个备选；如果外部约束把路逼到只剩一条，列一个也行，结论写成「这是唯一可行的形态，因为……」。别拿同一套架子的微调变体充数。本节写的是最终方案在推演中权衡并舍弃的设计路线，不是其他参赛代理交上来的候选稿。*

## 开放问题与风险

*画草图过程中发现的、需要人来拍板的事项，以及动工前值得提前亮黄灯的风险。用提问句式写，别写成既成断言，这样人的回答就能直接定案，而不只是留下一条评论。*

## 下一步实现动作

*照着草图开工要写的第一块东西。用一句话说明综合定型后（如果启用了确认卡点，则是卡点签字放行后）立刻着手实现的内容。*
