# Architect

先用 `not implemented` 空实现和伪代码勾勒出类型定义、函数签名、类形状和模块边界。综合多个模型的视角定型后，再照着选定的草图补全实现代码。

## 开工起手式

动工前先建一份待办清单，每个阶段占一项：

1. 摸底（Ground）
2. 画草图（Sketch）
3. 对齐确认（Agree）
4. 按图实现（Implement）
5. 推倒重来（Scrap）

## Phase A：摸底与定框

对新代码碰到的每一个系统都建立真实的心智模型。顺着相关子系统追一遍代码，光报个文件名不算摸底。给每个相关子系统写一段架构说明。如果这次设计会重新划定归属权或分层，顺手对现有形态跑一遍 **why** `skill`，把历史设计缘由变成明确约束，别靠猜。

只有在纯绿地新项目、周边没有任何已有系统需要对接时，才跳过 Phase A。

## Phase B：画架构草图

把架构草图任务连同 Phase A 的摸底产物一起交给 **arena** `skill` 去跑。把 `references/runner-prompt.md` 作为每位参赛代理的 `prompt` 传进去。

参赛模型取自 `pstack-models.mdc` 规则里的 `architect runners` 行，替换掉原来的 `arena runners` 行。如果规则文件或该行缺失，默认使用 `claude-fable-5-2-high`、`claude-opus-5-5-high-fast` 和 `gemini-4-carbon-high`。别名项与被拒模型的回退规则遵循 **arena** `skill` Phase A 的参赛代理规则。

同一问题设计两套。哪怕第一套方案看着已经够用，综合定型前也必须产出至少两个结构上截然不同的候选方案。这就是把 **exhaust-the-design-space** `principle` `skill` 落到实处。要的是整体形态迥异的替代方案，不是在同一个架子里小修小补。

综合前，拿 [`references/design-red-flags.md`](references/design-red-flags.md) 给每个候选方案过一遍排雷筛查。默认下一个接手改代码的人是一个只看得到自己打开那几个文件、顺手抄最近范例、挑最快能编过的路径走的代理。优先选那种「光看单个文件怎么改觉得顺手，放进全仓也依然正确」的设计。

在可行的候选方案之间比拼接口深度。优先选对外接口更小更简单、却在背后藏住更多复杂度的方案。一个承载能力扎实的接口可以把能力集中在一处，缩短调用链，而不是把逻辑摊薄散落到好几层里。

`arena` 会返回一份综合定型后的设计包，它的综合取舍结论直接填入设计缘由文档的「综合取舍结论」一节。

## Phase C：对齐确认（可选开启）

默认动作是拿着综合定型后的设计直接进入实现，不设人工审批卡点。

只有当调用者明确要求（例如「`/architect` 带确认卡点」「动手实现前先停下给我看」或类似说法）时，才启用卡点，把综合设计摆出来暂停等签字放行。

无论是否开启卡点，这份综合草图都可以单独打成一个 commit 提交，对应 **foundational-thinking** `principle` `skill` 里的「先搭脚手架」模式。按 **outcome-oriented-execution** `principle` `skill`，补全实现期间出现计划内、范围可控的临时破损是可以接受的。如果想在动工前先给设计上对抗压力测试，对综合后的草图跑一遍 **interrogate** `skill`。

如果人对这个架构形态提出异议（无论是在卡点阶段还是事后），把反馈当作 Phase A 的新证据，重新摸底并重跑 Phase B，再继续写代码。

## Phase D：照着草图补全实现

把 `not implemented` 替换成真实代码，把伪代码落成具体逻辑。综合后的草图就是契约。实现过程中出现的偏离都是需要浮出水面的信号，绝不要悄悄吞下硬凑。如果某个函数突然需要草图里没预料到的参数，立刻追问：是草图设计错了、漏了需求，还是当前实现越界了？

## Phase E：架构错了就果断推倒重来

如果实现过程不断冒出草图消化不了的别扭之处，直接把草图扔掉。按 **redesign-from-first-principles** 和 **fix-root-causes** `principle` `skill`，绝不要往错误的设计上硬打补丁。

判断依据是反复出现的*模式*，而不是一两处孤立个案。典型信号包括：

- 同一种别扭的绕过写法在互不相关的代码里反复冒出来。
- 好几个互不相关的边界情况全都需要单独加特判分支。
- 类型必须靠逃生舱（`any`、强转、实际永远非空却被迫标成可选的字段）才能编译通过。
- 草图明明说状态不共享，写着写着却条件反射觉得「这里得加把锁」。
- 调用方必须摸清抽象内部的潜规则才能用对它。
- 实现过程里在不同位置独立出现了两处及以上同形态的 Phase D 契约偏离。

保持工程判断力。零星几个边界情况不足以判一个架构死刑。有些问题本身就天然复杂，数据本身的复杂度不等于设计的复杂度。

决定推倒重来时，按下面四步走：

1. 梳理一遍目前已经搭出来的东西。
2. 按 `redesign-from-first-principles`，当作新冒出来的约束从第一天起就是基础假设，重新设计。
3. 按 **subtract-before-you-add** `principle` `skill`，先做减法再做加法。新草图在往上长之前，体量应该先比旧草图更小。
4. 回到 Phase B 重跑 `arena`。

## 交付产物

先写调用方用法，再由用法倒推出类型草图。小改动交给一个包含新类型与签名的文件；大改动交一份模块分布图外加类型定义。随草图一并交付按 `references/rationale-template.md` 写就的设计缘由文档，里面包含用法草图与综合取舍结论。
