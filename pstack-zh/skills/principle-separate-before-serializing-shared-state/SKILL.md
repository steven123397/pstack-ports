# Separate Before Serializing Shared State

当多个并发执行体可能共享可变状态时，先问它们到底需不需要共享同一个可变对象。不需要就直接拆开消除共享。确实必须共享时，靠结构强制串行化，比如锁文件、顺序阶段或独占所有权。口头指示和约定不算并发控制。

**为什么这么做。** 对共享状态的并发写入会制造竞态条件，时隐时现、极难复现，查起来代价极高。

**做法：**
1. **先标出共享的可变状态**（两边都会读写的同一个文件、两边都会推送的同一个分支、两边同时定义和消费的接口）。
2. **默认动作是消除共享的写入目标。** 问自己，这些执行体是真的需要维护一份权威对象，还是各自在发布互不干扰的事实？给每个执行体分配它独占的文件、键、分支或状态目录，只在读取或汇总汇报的边界把它们合起来。两个 worker 往同一个 `state.json` 里写各自的 `lastX` 字段，依然属于共享写入；拆成 `indexer-state.json` 和 `metrics-state.json` 才不算。
3. **只有当单一共享写入目标是真正的不变量时，才在结构上串行化访问**（锁文件、顺序阶段、单写者执行体或原子 CAS）。一旦脑子里冒出「咱们加把锁吧」，先把它当成一个需要复查的设计坏味道，别当成默认答案。
