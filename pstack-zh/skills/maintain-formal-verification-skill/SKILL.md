# Maintain a formal verification skill

形式化检查证明的，永远只是「它所描述的那个对象」的性质。一旦代码改了、验证没跟着改，检查照样可能一路绿灯，可它证明的早已是不复存在的旧代码。这种假绿灯最危险，因为它长得跟真证明一模一样。本 `skill` 就是给 `/create-formal-verification-skill` 生成的验证 `skill`（或任何针对具名代码跑模型检测器、证明器或源码级验证器的项目级 `skill`）准备的定期同步循环。代理按项目级验证 `skill` 干活时，改动当时就会被校准；本 `skill` 专治那些绕过了它的变更，包括合入的 PR、没挂 `skill` 的直接改动，以及跨越多条 commit 慢慢积累下来的漂移。

## 巡检结果枚举

给每道检查标明以下四种结论之一，并明确说出是哪一种：

- **in sync：** 自上次同步以来没有任何改动影响验证所描述的内容，且检查通过。
- **updated：** 代码变了，验证已更新至忠实描述新代码，且检查通过。
- **bug：** 验证忠实描述了当前代码，而当前代码违背了性质。这是代码里的真实发现，不是验证漂移。
- **blocked：** 验证无法拉回同步，或者根本跑不起来。准确说明卡在哪。

同一道检查可以同时是 `updated` 加 `bug`：更新之后验证重新对上了当前代码，随后性质在当前代码上跑挂了。

## 允许编辑的范围

只允许修改验证本身，包括模型、验证 `harness`、性质文件和验证 `skill` 本身。除非用户明确要求，巡检期间绝不要修改产品业务代码。当性质在当前代码上跑挂时，绝不要削弱性质或改歪模型去凑通过，直接上报失败。

## 同步校准流程

1. **找出所有形式化检查。** 验证 `skill` 没有固定文件名，按它的功能去找，即针对具名代码跑模型检测器、证明器或其他验证器的项目级 `skill`。通读找到的每一份（或用户点名的那份）。对每道检查，收齐五样信息：验证的性质、覆盖的代码范围、边界与假设、运行命令，以及上次确认与代码一致的同步基准 commit。如果项目里根本没有验证 `skill`，直接停下并指引去跑 `/create-formal-verification-skill`。如果 `skill` 里没记同步基准 commit，改用最后一次修改验证文件的那条 commit，并在报告里如实说明。

2. **原样先跑一遍。** 动任何文件之前，把每道检查先原样跑一次并记下结果。这里跑过并不证明当下代码正确，只证明旧描述本身依然自洽；这里跑挂则既可能是漂移也可能是真 bug，留到第 5 步再下定论。

3. **通读被覆盖代码的每一处改动。** 把被覆盖文件从同步基准 commit 到当前 commit 的 diff 拉出来读完，并逐条读 commit 信息。同时排查被挪动的代码：一个被覆盖的函数就算改了名、拆了分或搬到别的文件里，依然属于被覆盖代码。还要排查新写出来、却碰了受保护状态的新代码（比如一个新函数在写同一批字段）。对每一处改动，归入下面四类之一：
   - **无影响（No effect）。** 改动不触及验证描述的任何内容，比如格式调整、注释或验证未覆盖的路径。必须对照模型或 `harness` 核实，别轻信 commit 信息。
   - **验证不再描述当前代码。** 原先一步不可分割的操作被拆成了两步、增删了分支、某道检查挪了位置、多了通向受保护状态的新路径，或者某个变量的取值范围变了。模型或 `harness` 必须跟着改。
   - **代码承诺被有意改变了。** 改动改变了代码对外承诺的行为，而且改动里自带明确证据证明这是有意为之（文档注释、测试、changelog 或 commit 信息）。性质规约必须跟着改，并且你必须引用那份证据。
   - **承诺可能被打破了。** 代码变了，却没有任何证据表明承诺有意改过。后续冒出来的失败一律按代码 bug 候选对待。

4. **对着代码改验证，绝不对着结果凑验证。** 修改模型或 `harness`，让改动过的每一处重新对应到评审人打得开的真实代码，继续守住「代码里不可分割的一步在验证里也是一步」。先对着源码改完再重跑，绝不要为了凑绿灯去倒推改模型。只有面对「承诺有意改变」的情况才修改性质规约，并写清旧表述、新表述和依据证据。除非改动导致原边界本身出错，否则保留原有边界；如果不得不缩小边界，必须在报告里明说。

5. **重跑并裁定每项结果。**
   - **通过（Pass）：** 检查完全可能因为描述失去检测能力而假过。对着新代码故意构造一处违背性质的破坏（比如删掉新加的检查或调换新步骤顺序），确认更新后的检查确实能抓到它，再撤销这处破坏。
   - **失败（Fail）：** 拿着反例路径对着真实源码一步步重放。只要其中有一步在真实代码里根本不可能发生，说明是验证写错了，修好验证并说明错在哪。如果每一步在真实代码里都能发生，那就是真 bug。点名引入它的 commit，用代码自己的业务词把反例写成一串步骤，并用一句话说清危害。如果顺手能用低成本测试或复现脚本在真实代码上跑出这个 bug，把实证放进报告里，但不要提交进产品代码。

6. **更新验证 `skill`。** 同步更新每道检查覆盖的代码清单、运行命令、边界、假设和同步基准 commit，把同步基准 commit 推进到本次核对完的 commit。对于 `blocked` 的检查，绝不要推进它的同步基准 commit，并在报告里说明。最后像下一个代理一样照着更新后的验证 `skill` 完整走一遍，确认每一步依然跑得通。

## 报告内容

针对每一道检查，向用户交代五件事：

- 最终结论，以及你读过的 commit 范围；
- 验证里改了什么以及原因，每处改动给一句简短理由：是代码形态变了，还是承诺有意变了（附证据）；
- 重跑结果，以及你用来证明「更新后的检查依然能跑挂」的那次故意破坏演练；
- 每一个真 bug，用大白话写清：以代码业务词表述的反例步骤、危害，以及引入它的 commit；
- 验证目前仍然没覆盖到的盲区，包括本该纳进来却还没覆盖的新代码。

明明白白点出哪些失败是验证漂移、哪些是代码真 bug。如果某道检查更新前明明过了、更新后反倒挂了，直接说明之前的「通过」跑在一份过时的旧描述上。

把验证本身的更新单独放进一个独立变更里，与任何产品代码修复分开。
