# 动手前先读懂代码

在没摸透代码的情况下直接动手改，最容易埋下隐蔽的回归 bug。这对人如此，对代理更是如此。代理干砸活通常就两种原因：要么误解了你要什么，要么压根没掌握把活干对所需的上下文。第一个问题靠 [一条好 `prompt` 最多装这五件事](./02-poteto-mode.md#一条好-prompt-最多装这五件事) 解决，第二个问题就靠这一页。

`pstack` 给了你四个摸底入口：`/how` 讲清楚代码现在怎么跑，`/why` 挖出当初为什么这么写，`/teach` 把两件事揉成一篇讲透的教程，`/recall` 帮你把某个话题的近期上下文重新拼起来。这几个入口还有个隐藏好处，它们逼着代理把理解用你能核对的话讲出来。哪怕代理比你更熟这片代码，你也能靠这个把它管住。

## 先来一轮只读调研

原因还没搞清之前，先要调查结论，别急着要修复代码：

```text
/poteto-mode 查一下后台任务为什么每隔几小时就超时。把已知事实、你查了哪些数据，以及最可能的假设列给我。先别改代码。
```

「先别改代码」会把这条请求直接路由到 [Investigation playbook](../../skills/poteto-mode/playbooks/investigation.md)。它会顺着代码追踪，遇到动机类疑问就调 `/why`，最后给你一份带出处的解释。如果是多方案选型，它会给推荐结论加一张权衡对比表。顺口问一句「你查了哪些数据」，能逼着代理把确凿证据和猜测拆开写。等调查把根因指明了，再另起一个新任务去修。

## 用 `/how` 摸清运行机制

```text
/how 我们是怎么给通知去重的？查订阅者列表时有没有 N+1 问题？
```

直接问你心里真正想知道的问题就行。[`/how`](../../skills/how/SKILL.md) 会读完代码，按资深工程师带你上手子系统的水准讲清楚：运行时调用链、核心类型定义，以及容易踩坑的非直觉细节。它会派一个只读子代理一口气摸清代码并写出架构讲解。

## 用 `/why` 挖出历史决策

```text
/why 重试次数上限当初为什么定成 5 次？这个理由现在还成立吗？
```

[`/why`](../../skills/why/SKILL.md) 只从历史记录里找答案，不对着代码瞎猜。它会去翻引入这段代码的 commit、PR 讨论和后续每一次修改记录，如果线索太薄再往其他渠道深挖。回答里会直接引用原作者写的话，把代理自己的推论明标为推断，并老实说明记录里哪些问题没有答案，因为「当初没人写下来为什么」本身就是一条关键信息。

`/why` 和 `/how` 拼在一起用非常顺手。当你怀疑一团乱麻背后肯定有历史包袱时，直接说 `先跑 /why 再跑 /how`。

## 用 `/teach` 彻底搞懂

```text
/teach 给我讲透这个 PR 是怎么改重试逻辑的。说服我它修的是根因而不是表面症状。
```

光看几句摘要不够解渴时，就用 [`/teach`](../../skills/teach/SKILL.md)。它会跑 `/how` 和 `/why`（小改动可能只跑其中一个），然后把查出来的东西织成一份大白话讲解，一张小图接一张小图往上搭。「说服我」这种问法特别好用，它把走马观花式的代码导览变成了一场你能逐条拷问的论证。

这套问法同样适合拷问代理自己做出的决定：

```text
/teach 讲讲你为什么选了这种写法而没用队列。你权衡了什么，为什么这么取舍？
```

让代理给你讲课，对它自己一样有用。只要得把设计讲明白，代理就必须老老实实读代码、给每个结论找实据，而不能含糊其辞糊弄过去。

## 用 `/recall` 重建近期上下文

```text
/recall 帮我接上上周导出功能那块做到哪了
```

[`/recall`](../../skills/recall/SKILL.md) 会翻你最近的聊天记录，再结合团队共享记录（工单、历史修复、还在报警的线上错误），交回一份紧凑的现状 `brief`，说清现在卡在哪、下一步该干嘛。旧对话里攒着很多新开代理不知道的背景，回头接旧话题时，先用它把上下文载回来，再喂新线索：

```text
/recall 找回我昨天在虚拟列表上的进度，然后读一下这份 bug 报告。
```

如果你想原样接着某一场具体的旧对话往下做，那是下面 `Session pickup` playbook 管的事，不用 `/recall`。

## 用 `Session pickup` 接管前任留下的分支

当另一个代理（或者上周的你自己）留了一个干到一半的分支时：

```text
/poteto-mode 接手这个分支。读一下决策日志，搞清哪些已经做完了，顺着往下干。别把干完的活重做一遍。
```

[Session pickup playbook](../../skills/poteto-mode/playbooks/session-pickup.md) 会把前任留下的轨迹当作权威起点。它先还原分支现状和之前的决策，标出准确的续接点，再对照原始目标核验继承下来的结论，而不是推倒从零再来。

**避坑提醒：** 千万别觉得「反正代理待会儿改代码时自己会读的」就跳过这一页的 `skill`。没建立心智模型就急着动手的代理，十有八九会在第一个看着像原因的地方打个表面补丁。先花点 token 跑一遍 `/how`，远比修完引出第二个 bug 便宜。
