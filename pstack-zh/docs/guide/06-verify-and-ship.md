# 实跑验证与合入 PR

「能编译通过」不算证据。[Prove It Works](../../skills/principle-prove-it-works/SKILL.md) 这条 `principle` 要求代理在宣布完成之前，必须对着真实产物实跑验证；而你的职责，是把「真实产物」做成代理能够直接检查的对象。这一页讲清楚怎么提前写明完成条件、核查实测数字、为项目生成验证 `skill`、用形式化方法验证单测难以触达的属性，以及怎么开 PR 并一步步推到合入主干。

验证通常是代理干活最慢的一环，因为这一步往往得卡着等真人来验。让代理自己就能把验证跑通，你就不再是瓶颈。如果跳过验证直接并行开更多代理，你只会收获一堆没人验过的半成品，最后还是得自己审。

## 一开始就把完成条件说透

第一条 `prompt` 就把「做到什么算完成」写明白，用什么大白话顺口就怎么写：

```text
/poteto-mode 给这个命令加上 JSON 输出。普通文本输出要保持逐字节一致，JSON 必须能正常解析，两种模式都在示例项目上跑一遍。把实跑证据发给我。
```

现在代理手里有了三条能直接跑出结果的检查项，而不是靠猜你满不满意。它回来的回复里应该带着确切的命令和输出。如果某项检查没法跑，靠谱的回复会直说「结论未定（inconclusive）」。一份没附任何证据却自信满满的回复，本身就是危险信号。

不同的改动配不同的验证手段：

- CLI 改动，直接跑真实的命令行。
- UI 改动，在跑起来的应用里把改动的流程完整走一遍。如果要求与参考图逐像素一致，[Visual parity playbook](../../skills/poteto-mode/playbooks/visual-parity.md) 会对着冻结基线做截图 diff，不靠肉眼估摸。
- 解析器或迁移脚本，拿保存下来的真实输入重放一遍。
- 性能优化，对比改动前后的真实 profile 数据。
- 存储层改动，把写进去的值真实读回来核对。

直接向代理要一份你自己能复查的实证产物：先挂后过的测试输出、修复前后的录屏、trace 文件或截图。如果修复已经合入了，让它在 `main` 上再跑一遍同样的检查。一份实打实的产物胜过天花乱坠的文字解释，因为你不用把整轮过程重跑一遍就能当场挑它的毛病。

面对一个看着很小、但心里不太踏实的 `diff`，用 [`/blast-radius`](../../skills/blast-radius/SKILL.md) 去查它可能会把别处哪里搞坏。它会找出让这个改动之所以安全的那一条核心事实，并且靠运行真实代码去证明它，而不是光靠嘴说服你。

## 用 `/benchmark-checklist` 核查实测数字

优化前后的对比数字，是最容易在不知不觉中测偏的证据。热缓存、一边跑了 debug 构建，或者要测的逻辑压根没落在计时区间里，都能跑出看似很有说服力的「大幅提速」。在把数字发出去或据此做决定之前，先跑一遍：

```text
/benchmark-checklist 写进 PR 之前，先核查一遍这个导出提速数字靠不靠谱
```

[`/benchmark-checklist`](../../skills/benchmark-checklist/SKILL.md) 会连问七个问题，且每一条都要求拿实跑证据回答：

1. 限制当前数字的瓶颈究竟是什么，为什么没法再快一倍？
2. 对比双方是否都按生产环境的调优配置在跑？
3. 测出来的成绩有没有违背物理上限（比如磁盘带宽或 CPU 核数）？
4. 跑的过程里有没有报错，或者吐出了错误结果？
5. 交替多跑几轮能不能复现，中位数和波动区间是多少？
6. 这点收益放到用户真正等待的端到端路径上，到底有没有意义？
7. 你以为测到的那段工作，真的发生在计时区间内部了吗？

最后它会给出明确判定：更快、更慢、无显著差异，或者结论未定，同时附上采样次数、波动区间和瓶颈限制因素。只要说不出瓶颈在哪，或者有一侧没按生产配置跑，它就会判成结论未定。`/poteto-mode` 在 `Perf issue` 和 `Hillclimb` 里已经自带了这套清单；你在流程外自己测了数，或者觉得别人报的数字好得有点假时，直接手动调它。它就是 [Explain the Number](../../skills/principle-explain-the-number/SKILL.md) 这条 `principle` 的实操落地版。

## 为你的项目生成专属验证 `skill`

上面那条 UI 验证的背后藏着一个硬前提：代理得有脚本化的手段去驱动你的应用。项目里现成就有的最好；如果没有，运行：

```text
/create-verification-skill
```

[`/create-verification-skill`](../../skills/create-verification-skill/SKILL.md) 调研的是你的代码仓库，不是拉着你做问卷。它会自己摸清用户能碰到哪些界面、应用怎么在本地拉起、用什么工具驱动最顺手（优先用项目现有 `harness`，没有的话再看浏览器加 CDP、PTY 或纯 HTTP）、什么产物能证明行为正常，以及两个实例能不能同时并跑。只有代码里实在查不到的事，它才会问你。

它会在 `.cursor/skills/verify-<app>/` 生成给代理用的操作手册，包含精确的 Launch、Doctor、Drive、Evidence 和 Cleanup 章节，附上配套辅助脚本的 Helpers 说明，并在 `features/` 下建一份 `Feature Map`（功能清单图），把应用支持的功能和各自对应的验收结果全部建好索引。这套 `skill` 自带一份 [完整的 feature-map 示例](../../skills/create-verification-skill/references/feature-map-example/)，里面有 README 总索引和按四个必填二级标题组织的单功能文件。在交给你之前，生成器必须端到端自证跑通一遍：拉起应用、跑 Doctor 检查、实际驱动一个功能、截取证据、清理现场，最后确认证据文件在清理之后依然完好。如果这一遍自证没过，就别用它产出的结果。

从那之后，「在应用里实跑验证一下」就成了仓库里任何代理拿来就能干的标准步骤，再也不用每次重头解释怎么启动项目。如果你想指定验收产物的形式，在 `prompt` 里顺口点出来就行：

```text
/poteto-mode 实现批量归档功能。用 /verify-<app> 验证你的改动，给我看录屏和截图作为证据。
```

```text
/poteto-mode 用 /verify-<app> 复现一下这个问题。如果在 main 上能复现，就修好并录个视频证明。
```

验证 `skill` 跑顺之后，[`/swarm`](../../skills/swarm/SKILL.md) 就可以按 `Feature Map` 里的条目并行分片，一口气跑完回归再汇总报告。你也可以撒出一组验证代理，在足够大的样本上确认性能收益，或者在 PR 合入前对应用做一轮回归轰炸测试。

把验证 `skill` 当成项目基础设施来维护，不要当成一次性脚本。把它提交进仓库，让团队里每个人和每个代理都用同一套标准驱动应用。接着遵循 [Build the Lever](../../skills/principle-build-the-lever/SKILL.md)：一旦发现代理老是在写一次性脚本去点界面，就让它干脆封装一个轻量控制 CLI 供验证 `skill` 调用。这样既省 token，每次运行也完全可复现。一个代理用着顺手的 CLI 通常具备这几个特点：

- 几个能自由组合、每个都干实事的命令，而不是一堆单薄的零碎小命令。
- 凡是带破坏性的操作都提供 `--dry-run` 选项。
- 子命令按层级渐进展开，不要一口气把几十个参数全糊在脸上。
- 报错信息里直接写明「应该改做什么」。
- 详实清晰的 `--help` 说明。
- 支持机器可读的输出格式，比如 JSON。

顺便把本地开发环境也做成一键可复现的：预置种子数据、固定测试账号，一条命令每次拉起的状态都一模一样。

## 定期校准，别让验证 `skill` 老化失真

应用在不断迭代，`Feature Map` 很快就会过时。至少每天跑一次下面这条命令，最好挂成定时自动化任务，免得靠人记着：

```text
/maintain-verification-skill
```

[`/maintain-verification-skill`](../../skills/maintain-verification-skill/SKILL.md) 会全面审计生成出来的验证 `skill`：先按功能并行派只读代理核对源码，再开一次真实运行会话把清单里的每个功能从头到尾跑一遍。最后只会有三种明确结果：`clean` 代表覆盖完整、无需改动；`changed` 代表开出最多一个 PR 修正经实证的偏差，且改动严格限制在验证 `skill` 自己的目录里；`blocked` 代表被卡住并说清阻塞点。它绝不会擅自改业务代码。如果实跑抓到了真正的产品回归 bug，它会直接报告回归，绝不会改文档把 bug 藏起来。

## 用形式化验证 `skill` 证明单测碰不到的属性

普通验证 `skill` 只证明你点过的那些路径。但有些要命的 bug 藏在没人会手动点到的角落里：两次重试刚好重叠、锁在写到一半时过期、状态变更乱序到达。单测极难撞上这些组合。针对这类出事代价很高的代码，运行：

```text
/create-formal-verification-skill
```

[`/create-formal-verification-skill`](../../skills/create-formal-verification-skill/SKILL.md) 会直接从代码里挑靶子：找那种代码对外许下了关键承诺、一旦违背就会坑到用户、而测试又很难覆盖到的地方。它挑的是最值得验证的硬目标，不是最好糊弄的软柿子。你也可以直接指定模块或 bug 让它从那里下手：

```text
/create-formal-verification-skill 检查一下任务租约和重试逻辑。同一个任务绝不允许同时运行两份。
```

问题类型决定工具选型。如果是检查事件会不会按错误顺序交错发生，最适合拿小模型做模型检测，无论你用什么编程语言默认首选 TLA+。如果是检查一段代码对所有输入是否都成立，就选直接跑在真实代码上的验证器；如果当前语言没有合适的验证器，代理会老实告诉你，并改用生成式输入直接测真实代码，不会手写一个脱离代码的假函数模型糊弄过去。如果某条性质必须在任意规模下都成立，则可能需要定理证明。代理会说清楚它选了什么工具以及为什么。

它验证一条核心属性时，一定会故意改坏一份代码副本，证明这条检查真的能把坏代码拦下来，因为一个你从没见过它报红的检查什么也证明不了。如果线上现有代码本身就已经违背了这条属性，你会拿到一份用你业务代码术语写成的最短反例步骤序列。属性定义绝不妥协放宽，问题就是问题。除非你明确要求，否则它不会擅自修改业务代码。

最后它会在项目本地生成一份 `skill`，告诉下一个代理怎么判断改动是否碰到了受验证代码、用哪一条命令重跑检查，以及怎么区分真 bug 和建模误差。交差之前，生成器会故意做一次临时破坏性改动并按这份 `skill` 走一遍，必须亲眼看到检查把坏改动抓出来才算数。交付说明里会交代清楚验了什么、用了什么工具和边界范围、查出了什么，以及哪些范围没覆盖到。验证通过只代表在所建模型和边界内成立，不代表整个系统万无一失。

这份 `skill` 还会记下每项检查对应哪些源码文件，以及上次对齐时的 commit。后续合并和重构如果绕开了它，检查就可能一直对着早就不存在的旧代码报绿。大改之后记得运行 [`/maintain-formal-verification-skill`](../../skills/maintain-formal-verification-skill/SKILL.md)，它会对照最新源码更新验证模型并重跑，确认每条检查依然具备抓坏代码的能力，并明确告诉你每个失败到底是验证模型漂移了，还是业务代码真出了 bug。

## 用状态图把行为画给人看

模型里的反例步骤足以说服工程师，但拍板业务行为的产品经理或设计师需要用他们看得懂的语言看到全貌。运行：

```text
/statechart 画出用户在离线状态下编辑笔记时能看到的所有状态变化
```

[`/statechart`](../../skills/statechart/SKILL.md) 会从 TLA+ 模型直接生成一张用户视角的 Mermaid 状态图，保证画出来的图和模型检测器校验过的模型绝不会各说各话。读图人关心的业务规则（比如「离线时界面绝不能显示已同步」）会直接写成不变量。图上会标出每一个违背规则的状态，报告里则用人话给出走到每个出错状态的最短操作路径。交稿之前，代理还会把每条 bug 路径在真实代码里复现一遍，避免把建模写错当成真 bug 报给对方。

## 开 PR

```text
/poteto-mode 开一个 PR。整理成小步有序的 commit，描述里带上实跑证据。
```

[Opening a PR playbook](../../skills/poteto-mode/playbooks/opening-a-pr.md) 会在 `worktree` 里把改动 rebase 成小步有序的 commit，清理 `diff`，给描述过一遍 `unslop`，最后把 PR 链接发给你。五个聚焦的小 PR 永远胜过一个臃肿的大 PR，叠栈跟进也永远胜过在一个分支上越堆越厚。

## 用 `Babysit` 把 PR 推到就绪可合入

PR 一开出来，各种阻碍马上就找上门了：检查挂了、评审提了意见、主干分支又往前走了。把这些琐碎拉扯交给 [Babysit playbook](../../skills/poteto-mode/playbooks/babysit.md)：

```text
/poteto-mode 帮我盯着这个 PR，把它跑绿。
```

`Babysit` 会持续盯盘（在 GitHub 上用内置 watcher 脚本，本地配了 Origin CLI 时优先用 Origin），严格按顺序清障碍：先解冲突，再清评审评论，最后修 CI。所有已知修改都会攒成同一波推送，好让 CI 只重跑一次，而不是每改一行就触发一轮。对待评论一律保持怀疑，因为真人和 bot 都常常把真 bug 和噪音混在一起提；真问题就修，噪音就贴上确凿反证直接驳回。如果只是想问一下现状，把需求说轻一点，`Babysit` 会直接查完就报，不会开启轮询循环：

```text
/poteto-mode 看看 PR 123，还有什么没清的吗？
```

`Babysit` 走到「已就绪可合入（merge-ready）」就会停手。就算全绿了它也绝不会擅自点 merge，因为合入是另一个独立的决定。

## 用 `Shipping` 把叠栈 PR 合入主干

全绿不等于安全。真准备合入主干时，明说：

```text
/poteto-mode 把这叠 PR 合入主干。
```

[Shipping playbook](../../skills/poteto-mode/playbooks/shipping.md) 在开启任何自动合并之前，会先对每个 PR 做独立验证：每个 PR 单派一个全新验证代理实跑一遍用户视角行为，而且负责裁定通过的代理绝不能是写这段代码的代理。接着 `Shipping` 只从栈底开始，按顺序逐个合入连续验证通过的那一段 PR（默认走 GitHub，本地有 Origin CLI 时走 Origin），一旦遇到第一个断链的 PR 就停下汇报。排在未验证 PR 上面的 PR 就算自己已经验过也得等着，因为直接合它会把底下的风险一起带进主干。
