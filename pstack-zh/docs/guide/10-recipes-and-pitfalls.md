# 实用套路与常见深坑

先放一批值得直接照抄的 `prompt`，再列一串几乎人人都会踩一遍的坑。把里面的路径和完成条件换成你自己的就行。这些模板刻意写得很口语、不端着，因为实际干活时大家就是这么敲的，各个 `skill` 都能准确领会意图。

![她正在品尝刚做好的菜，机器人们照着菜谱盒做饭，灶台上方钉着写有 /how、/tdd 和 /loop 的卡片。](./images/recipes.jpg)

## 摸清一个陌生子系统

```text
先用 /how 搞懂这套初始化流程是怎么跑的，再用 /why 查清楚它最近为什么坏了。
```

先看机制，再挖历史。每个 `skill` 交回的报告都会写明它查了哪些来源，方便你判断结论站不站得住脚。

## 面对杂乱反馈，动代码前先让它复述

```text
/poteto-mode 读一下这个讨论串，用大白话复述到底出了什么问题。先别改代码。
```

理解跑偏在复述这一步当场就会露馅，这时候纠正只花一条消息。等代理说完它的判断，再掏出你自己的猜测。只想让它复述一遍、不走 `playbook`，直接用 `/in-your-own-words`。

## 发 `prompt` 之前先用 `/sharpen` 磨深

```text
/sharpen 给新的计费服务写一份新人上手文档。
```

代理会列出顶尖专家会多做什么、会从哪份原始材料切入、用什么方法和工具，以及靠什么外部依据验证写对了。然后把重写好的 `prompt` 交回给你，它自己不会直接开工。你读着顺眼了再发出去。

## 挑方案前先看跑出来的原型

```text
/poteto-mode 给设置页布局做几个原型方案，挂在同一个切换开关后面，把每种效果截图发我。
```

对着能跑的东西选，别对着文字描述盲选。代理在搭原型的过程中也会顺手把布局和时序疑问自己试明白。

## 设计定下来之后转成实施计划

```text
/poteto-mode 把这份设计转成实施计划。拆成小步可验证的 PR，每个 PR 配好各自的验证证据。
```

等设计真稳了再要计划。计划文档本身就是交付物，末尾会标明接下来该由哪个 `playbook` 来落地执行。

## 给现有设计找第二意见

```text
让 /arena 对这个讨论串和我们现在的方案给个第二意见
```

你当前的方案会作为候选之一参与同场比拼，最终汇总会告诉你评审团到底有没有找到更好的解法，还是印证了你原来的思路。跟事后返工的代价相比，花这点 token 非常划算。

## 并行检查多个独立分片

```text
/swarm 用各自的 check.sh 把 packages/ 下每个包都验一遍。一包一个工人，汇总成一份报告。
```

每个工人只管自己那一个包。主会话收齐所有分片后，只交回一张标着 `PASS`、`ISSUES` 或 `BLOCKED` 的汇总表，不会把一堆原始日志糊你脸上。

## 带着怀疑态度审整个分支

```text
/interrogate 审一下整个分支，严格挑刺。先别改任何代码。除非是真 bug 或行为回归，不要报吹毛求疵的小毛病。
```

这些限定词真起作用。「先别改任何代码」把这轮锁成只读，而去掉琐碎挑刺的约束会提前滤掉噪音，留下的经实跑验证的问题才配得上你的时间。

## 用先挂后过的测试修 bug

```text
/poteto-mode 先复现重复写入的问题。如果本地有便宜好跑的测试路径就走 /tdd，然后修复并重跑验证。
```

「如果本地有便宜好跑的测试路径」这一句很关键。靠脆弱 mock 硬凑出来的单测，说服力不如直接跑真实命令，这条写法允许 `playbook` 实事求是做取舍。

## 带着实证复现并修复问题单

```text
/poteto-mode 用 /verify-<app> 复现一下。如果在 main 上能复现，就修好并录段视频给我证明。
```

「如果在 main 上能复现」允许它在 bug 已经消失时提前止损停手。录屏则让你在读一行 `diff` 之前先亲眼看到确实修好了。

## 证明单测极难撞上的关键属性

```text
/create-formal-verification-skill 检查重试队列。同一条消息绝不能投递两次。
```

你会拿到划定范围内的穷尽验证、如果现代码已经违背规则的话一份业务术语版最短反例路径，以及一个留在项目里的本地 `skill`，供后续改动那块代码时自动复查。

## 发出去之前核查一遍性能数字

```text
/benchmark-checklist 写进 PR 描述前，先核查一下这 40% 的提速靠不靠谱
```

它会给出更快、更慢、无显著差异或结论未定的判定，同时附上采样次数、波动区间以及真正卡住数字的瓶颈。

## 彻底堵死反复纠正的同类错

```text
/correct 代理老是新加配置开关却忘了注册进 schema
```

修法会通过架构、类型、lint 或测试直接落进仓库，让下一个代理从根上再也犯不了这个错。

## 只问怎么用，先别开工

```text
/poteto-help 怎么让 poteto-mode 每一轮对话都一直保持开启？
```

它会直接回答、给你一条现成的 `prompt`，再附上出处链接。在你自己把那条 `prompt` 发出去之前，不会启动任何耗 token 的任务。

## 离开前交代好过夜底线

```text
我去睡了，全自动一直跑到所有测试夹具全过为止，别停。记好决策日志，明早我要审。
```

完整约定见 [睡觉时让它接着干](./07-overnight.md)。当任务目标和完成条件已经在对话里说清时，这么短一句就够了。

## 一句话把跑偏的代理拉回正轨

纠偏 `prompt` 往往只要一行：

```text
我说的是先复现，还没让你直接改代码。
```

```text
按 Prove It Works 来，给我看真实命令输出，别拿编译日志糊弄。
```

```text
/unslop 一下，一个长破折号都别留
```

通常根本不需要长篇大论。点出正确的名字就行，[24 条 `principle` 速览](./08-principles.md) 就是你的现成词典。

## 把晦涩回复翻成大白话

```text
/bro
```

整条 `prompt` 就这四个字符。[`/bro`](../../skills/bro/SKILL.md) 会把上一条消息缩成毫无术语的大白话，像真人在对面跟你聊天一样。碰到技术上滴水不漏、但你读完还是云里雾里的回复时，直接敲它。

## 回来快速追上挂机进度

```text
/ketchup
```

[`/ketchup`](../../skills/ketchup/SKILL.md) 用大白话告诉你自你上一条消息以来发生了什么变化，然后列出每一项等你拍板的事，带上推荐选法、证据和风险。整个汇报过程只读不改任何东西。

如果想直接看短视频版进度同步，敲 [`/ketchup-video`](../../skills/ketchup-video/SKILL.md)。它会把过程做成带字幕的简短幻灯片视频，视频下面用文字排好等你拍板的事项。

## 常见踩坑清单

- **在 `prompt` 里手列一串 `skill`。** 「先用 `/architect`，再用 `/arena`，然后 `/interrogate`」会把 `playbook` 本来排好的顺序打乱甚至漏步。直说目标和硬约束，只在想覆盖默认行为时才点名某个 `skill`。
- **给一个没法判定对错的完成条件。** 「把它弄好一点」让 `/loop` 根本无从检查。必须给一条能明确跑出通过或失败的命令或产物。
- **一上来就抛出你猜的根因。** 代理会顺着你指的方向钻牛角尖。先让它复述问题，再聊你的直觉。
- **直接拿第一个设计开工。** 只试一次就会锁死模型蹦出来的第一个形状。先要原型或跑 `/architect`，对着实证选。
- **死磕一份没写过代码的纸面计划。** 拿对抗评审去审一份背后没代码的计划，只会催生一堆现实里压根不会发生的假想风险。先拿原型把疑问定死，真东西做出来再审。
- **让多个并行代理挤在同一个 `worktree` 里。** 它们会互相覆盖文件，最后谁也说不清哪行是谁改的。要么跑云端代理，要么明确要求「每个尝试独立开一个 `worktree`」。
- **还没建立信任就开过夜循环。** 不能自证结果的循环只会更快地批量制造烂摊子。先把项目验证 `skill` 跑顺。
- **轻信没核查过的跑分数字。** 热缓存或者压根没跑进目标路径都能伪造出漂亮提速。数字放出去前先过 `/benchmark-checklist`。
- **老在聊天里手工纠正同一个错误。** 对话里提醒一次只管这一轮；跑 `/correct` 改仓库，以后所有代理都不会再犯。
- **拿 `/arena` 当并行覆盖工具用。** `/arena` 是多路跑同一份设计或代码 `brief`，再选基底、嫁接优点；分片覆盖或按规则赛马汇报，应该用 `/swarm`。
- **评审评论照单全收。** 机器人和真人都常常把真缺陷和噪音混在同一张列表里。`/interrogate` 只保留重跑能证明的缺陷，并列出刷掉了什么及原因，两边你都可以推翻重判。
- **把 `auto` 当成一个真实模型 `slug`。** `auto` 和 `inherit-parent` 的意思是「调用子代理时省略模型字段，直接继承主会话模型」。详见 [安装与配置](./01-setup.md)。
- **看着编译变绿就宣布成功。** 编译只证明语法过了。要真实命令输出、应用操作流、落库实值或性能 profile，并且把证据贴进回复。
- **徒手裸写 `SKILL.md`。** 走 [Authoring or modifying a skill playbook](../../skills/poteto-mode/playbooks/authoring-a-skill.md)，把 frontmatter 校验和评审流程一起带上。
